### 2026-09-17 — Phase 4: type system

- Picked up the "Next job" note above. Two spec §12 open questions were flagged as blocking before any code got written, resolved with Hamed:
  - **Item 10 (built-in vs. `&`-prefixed disambiguation):** a closed set of 8 built-in names (`SUM`/`COUNT`/`AVG`/`MIN`/`MAX`/`EXISTS`/`ALL`/`ANY`) may only be called bare; any other bare call is an error pointing at `&name(...)`; the 8 names are reserved (a user `fn` can't be declared with one). Written up in new spec §5.3.1, including a formal signature table for the 8 built-ins — nothing had formalized these before, only shown them by example.
  - **Item 11 (query-tailed function return type):** a function whose tail is a `Query` always returns `JSON` — an array of the selected shape (`SELECT *` → array of objects; `SELECT <col>` → array of that column's type). Declared return type must be `JSON` for a `Query`-tailed body, checked once at the `FunctionDecl`. Written up in new spec §8.6.
- Implementation:
  - `src/language/minab-types.ts` (new) — `MinabType`: `scalar` (mirrors the grammar's `TypeRef`) / `tuple` / `record` (a single related row) / `collection` (a to-many relation) / `null`. Replaces `schema.ts`'s `MinabColumnSchema.type: string` with a structured `ColumnType` (`scalar`/`ref`/`collection`), and upgrades `MinabFunctionSchema`'s fields the same way. Also: `isAssignableTo` (assignment/initializer compatibility, stricter than plain equality about nullability), `baseTypesEqual` (operator compatibility), `widenNumeric`.
  - `src/language/minab-builtins.ts` (new) — the 8 built-in signatures, each a small polymorphic type-checking function (not a static signature) since e.g. `SUM`/`MIN`/`MAX` operate over an arbitrary element type.
  - `src/language/minab-type-checker.ts` (new) — `MinabTypeChecker.inferType(node: Expression)`, following the same `{ok,reason}` discriminated-union pattern `MinabScopeResolver`'s `ScopeResolution` (Phase 2) already established.   - **A design gap the task list hadn't named:** a top-level validation rule (spec §6 — record- and field-level rules, the language's primary use case) has no statically-known table under Phase 2's scope resolver, by design — nothing in Minab source ever names it. Left as-is, `.field` at the top of *every* such rule would have been untypeable, breaking the central use case. Per the traversal rule (§3.1), `.customer` is the *related record*, not its key, so this is a genuine type mismatch, not a checker bug. Fixed all four to `.customer.id == customerId` (or the join equivalent). Confirmed empirically (a throwaway parse test: the spec's form fails, the showcase's parses clean) before touching anything. Fixed the spec example to match §4.1's clause order and the §11 grammar — both of which are unambiguous, so this was a plain correction, not a design question. It's now also covered for real: `test/sql-compilation.test.ts` compiles that exact example.
  - **The ADR's DML claim was too broad.** It said "every DML form in §10 already names a single target table per statement" — but §10 explicitly allows a `JSON`-array field as a target, which is not a table at all, and §3.5 confirms the ordinal DML forms (`DELETE .customers[2]`, `WHERE .$index > 2`) are *only* legal against a `JSON`/`T[]` source. Rewrote that section to split relational targets (SQL DML) from `JSON`-array targets (interpreted read-modify-write), which lands on the same seam as the rest of the ADR.
  - **The ADR silently assumed a SQL dialect where the spec deliberately doesn't.** §7.2 calls the type vocabulary "storage-agnostic"; the ADR emits Postgres-flavored SQL. Not a contradiction (a compilation target isn't a type mapping) but worth stating, so a consequence now records it, notes `IS [NOT] DISTINCT FROM` is standard SQL rather than Postgres-only, and names the per-dialect equivalents. Also added the `CITEXT` consequence: compiled against a real `citext` column equality is case-insensitive for free, so the *interpreter* has to match that deliberately or the two runtimes silently disagree.
  - One citation fix (implicitly-async `fn` is stated in §8's preamble, not §8.1).
- Implementation, per the ADR's own "Phase 5 implementation scope":
  - `src/language/minab-sql-compiler.ts`, `src/language/minab-interpreter.ts`, `src/language/minab-executor.ts` — see `docs/roadmap.md` Phase 5's "What actually shipped" for the full breakdown. Both services wired into `minab-module.ts` alongside the existing four; the host's connection and the record under evaluation are passed per call to `interpreter.evaluate`, not baked into `createMinabServices`, since they're per-invocation rather than per-embedding.
  - `src/language/schema.ts` gained `foreignKey` (on `ref`/`collection`) and `primaryKey` (on a table). This was forced by implementation, not planned: Phases 2-4 only ever needed to know *what* a traversal lands on, but executing one needs to know *how* — `.customer.country` is a join, `COUNT(.orders[...])` a correlated subquery, `. != ^` a comparison of row identities. Both optional, so existing hosts/fixtures keep working and an undeclared relation fails with an explicit reason rather than guessing at a naming convention. Also closes the primary-key gap Phase 4 flagged when it found the four `ref`-compared-to-scalar defects.
- Three judgment calls worth a second look, each documented where it lives:
  - **`ref` traversal compiles to a correlated scalar subquery, not a join.** Chosen for §7.7 rule 1: traversal through a null `ref` must evaluate to `null`, and an inner join would drop the row instead. A `LEFT JOIN` would also work but has to be hoisted into the `FROM` clause; the subquery is local to the expression and a planner can usually flatten it.
  - **The pushdown boundary is the *smallest* table-touching subexpression, not the largest compilable one.** The compiler can bind local values as parameters, so it would happily swallow a whole rule — but `COUNT(.orders) < 5` pushed down whole compiles the `5` to a bare placeholder, leaving SQL comparing two untyped parameters (which real Postgres rejects). Pushing down the smallest node that actually needs the database keeps every generated statement grounded in real columns, and keeps the operators themselves under the interpreter's null/`CITEXT` rules.
  - **A user-written `==` compiles to `IS NOT DISTINCT FROM` even in a `JOIN ... ON`**, which reads oddly for a join but is what §7.7 literally says. The compiler's *own* synthesized join predicates are the opposite case and stay plain `=`, so a null FK matches nothing.
- Two gaps the end-to-end tests caught that the SQL-diff tests alone would not have: `$` had no compiled form at all (a field rule's `EXISTS(#Customer[.id == $])` failed), and a relation reached off the *outer* record rather than a query scope wasn't recognized as a collection (`COUNT(.orders[...])` at the top of a rule). Both fixed. A third was a masking bug — a genuine failure inside a real collection (an undeclared foreign key) was being swallowed and re-reported as the generic "that isn't a collection", which is exactly the kind of message that wastes someone's afternoon; the structural check now runs first so the real reason survives.

- Picked up from the "Next job" note above, which listed the three leftover execution features *before* Phase 6. Hamed asked for Phase 6, so it went first; the three are unchanged and are back at the top of the next job list.
- Implementation (`src/cli/`, four files, no language behavior of its own — everything is a front end over the services Phases 1-5 built, which is why this phase is marked Mechanical):
  - `main.ts` — `check` / `compile` / `run`, plus arg parsing, config loading, and result rendering (rows as an aligned table, a rule's answer as a value, `--json` for either). `runCli(argv, io)` takes its argv and output sinks as parameters rather than reading `process.argv`, so the test suite drives whole commands in-process and asserts on exactly what a user sees; `bin.ts` is the shebang wrapper that supplies the real ones, and `package.json`'s `bin` points at the built `out/src/cli/bin.js`.

- `examples/` — the §6.1 correlated rule and the §4.3 grouped query, plus their config; both are what the README walks through. README rewritten (it was still describing the Phase 0 bootstrap, claiming "no semantic services are implemented yet", four days and six phases out of date).
- Three defects, each found by running the thing rather than by reading it:
  1. **A stack trace instead of a diagnostic.** `MinabTypeChecker.inferType` assumed every child node exists. A file with a syntax error (`.a >> .b` recovers to a `BinaryExpression` with no `right`) crashed it with a `TypeError`, which Langium caught and re-reported as a validation-time exception — the exact "stack trace, not readable output" this phase's task list names. Guarded at the top of `inferType`. Worth noting this was never a CLI-only bug: Phase 7's language server validates on every keystroke, so it would have hit an editor mid-expression constantly.
  2. **2.8 seconds of startup, every invocation.** Measured, then bisected: it is not parsing, it is Chevrotain re-validating the whole grammar on parser construction, which Langium does whenever `LanguageMetaData.mode` is `development` — what `langium generate` writes. The same construction in `production` mode takes ~80ms. `createMinabServices` gained a `MinabServiceOptions` parameter for this and the CLI passes `{ mode: 'production' }`; the test suite deliberately stays on `development`, where those ambiguity warnings are the safety net the Cursor grammar-workflow rule relies on. CLI startup is now ~0.25s, and `test/cli.test.ts`'s 32 cases run in ~1s instead of ~60s.
  3. **One mistake, three identical messages.** `MinabValidator` registers type checks on every expression node, so an error inside a subexpression is re-reported by each enclosing node that re-infers it, over a widening range. The CLI keeps the innermost and drops the rest. Deliberately fixed at the presentation layer and flagged rather than changed in the validator — see "Next job".

Both gaps this file has carried since Phase 5 — "the generated SQL has only ever been diffed against hand-written expected SQL, never executed" and "`CITEXT` case-insensitivity is asserted in the interpreter but assumed in the compiled path" — are closed for everything those six cases touch. ### 2026-09-18 — Phase 7: IDE tooling (LSP + VS Code)

- Picked up the "Next job" note above. Fixed the carried-forward duplicate-diagnostics issue first (Phase 6/status.md both flagged it as belonging here, "probably at the validator"), then did the roadmap's three tasks in order: module switch, language server + VS Code extension, hover/go-to-definition.
- **Duplicate diagnostics, fixed at the validator.** Root cause: `MinabValidator.checkExpressionTypeChecks` is registered on 11 container expression types whose own `inferType` recurses into their children's — a failing child that's also one of the 11 gets independently re-inferred and re-reported by every registered ancestor above it. Fix: `TypeResult`'s failure branch gained `origin?: AstNode` — the node whose own inference first produced the failure. `MinabTypeChecker.inferType` became a thin public wrapper (`inferTypeDispatch` is the old body) that stamps `origin` once; since every recursive call already went through the public method, this needed zero changes to any of the ~57 `err(...)` call sites — the origin just settles on the innermost failing node by construction. The validator now only reports `when result.origin === node`. Verified this actually catches the pre-existing bug, not just plausible in theory: temporarily reverted the guard, confirmed `test/typechecking.test.ts`'s new regression case failed with 2 diagnostics instead of 1, then restored the fix.
  - **One approach tried and reverted:** broadening `checkExpressionTypeChecks`'s registration from the 11 concrete types to the whole abstract `Expression` type (so origin-tracking alone would need no enumerated list, and would also close a pre-existing gap where `ParentRecord`/`NameRef`/`Subquery` — which have their own direct failure paths but aren't in the 11 — go unreported when nested under a registered ancestor). This broke three passing tests: `Expression` includes node types that are never independently inferred, only ever consumed by a specific parent (`is`/`isnot`'s `array`/`object`/`string`/`number`/`boolean` kind markers; a bare call's callee, which is a real `NameRef` AST node, e.g. `COUNT` in `COUNT(...)`) — calling `inferType` on them directly, which the broadened registration does by visiting them, produced spurious "cannot infer a type"/"unknown name" diagnostics on perfectly valid programs. Reverted to the original 11-type list. The `ParentRecord`/`NameRef`/`Subquery` gap is therefore still open, unchanged from before this session — narrower than the roadmap asked this fix to cover, but the safe call given what broadening it actually did to real programs.
  - Also removed `src/cli/main.ts`'s `dedupe`/`rangeKey`/`contains` — the CLI-only post-pass this makes redundant.
- **Module switch.** `src/language/minab-module.ts` now builds on `langium/lsp`'s `createDefaultModule`/`createDefaultSharedModule` instead of the core-only ones; `MinabServices` is `LangiumServices & MinabAddedServices`. Confirmed before touching it that `DefaultSharedModuleContext` (the new context type) is a strict superset of the old core one, so `createMinabServices`'s existing call sites (the CLI, every test file, all using `NodeFileSystem`/`EmptyFileSystem`) needed no changes — verified by full build + test run, not just by reading the type.
- **Language server.** `src/language/main.ts` (new): `createConnection` over stdio/IPC, one `MinabSchema`/`MinabRuleContext` for the whole server process from `minab.config.json` (found the same way the CLI already does — exported `discoverConfig` from `src/cli/config.ts` for both to share), then `startLanguageServer`. Smoke-tested the compiled server directly (`node out/src/language/main.js --stdio`) — starts clean, no errors; confirms the wiring works independent of any IDE.
- **Hover/go-to-definition for `#alias`.** `src/language/lsp/minab-hover-provider.ts`/`minab-definition-provider.ts` (new). The default Langium providers key off the Linker's resolved cross-references, which Minab has none of (Phase 2's own finding — `#alias` is resolved by `MinabScopeResolver`, not the grammar). Both call `resolveNamedScope` directly — the exact resolution the `Validator`'s own `NamedScope` check already uses — and point at the declaring `Query.alias`/`JoinClause.alias` CST node. `test/lsp.test.ts` (4 tests) exercises both directly against a `parseHelper`-built document, no real JSON-RPC connection needed, the same pattern the scoping/validation test files already use.
- **Syntax highlighting.** Added `textMate.out` to `langium-config.json`; `langium generate` now also writes `vscode-extension/syntaxes/minab.tmLanguage.json`, derived from the grammar's own keywords/tokens — confirmed non-trivial output (real keyword/string/comment scopes), not a stub.
- **VS Code extension.** `vscode-extension/` — a separate, non-workspace npm package (its own `package.json`/`node_modules`/`tsconfig.json`; this repo has never had npm workspaces and the extension is a different publishing target — a `.vsix`, not an npm package — from the CLI). `src/extension.ts` starts a `LanguageClient` pointed at the root package's compiled `out/src/language/main.js` by relative path, no npm dependency between the two since neither is published. `contributes.languages`/`contributes.grammars`/`language-configuration.json` (hand-written, ~20 lines, standard brackets/comments) wire up the rest. Built clean (`cd vscode-extension && npm install && npm run build`).

### 2026-09-19 (continued) — The web playground (merged after Phase 9)

- New `playground/`: a standalone Vite + React + TypeScript package (like `vscode-extension/`, not a workspace). It runs the whole toolchain in the browser: the Langium services in a Web Worker, with [PGlite](https://pglite.dev) (PostgreSQL compiled to WebAssembly) as the database. Pages: a landing page with live snippets; `/play`, a workbench with Monaco, output tabs Result/SQL/Execution/Problems/AST, and a host panel Schema/Data/Record/Field; a 12-lesson tour whose goals are checked against the engine; a 29-example gallery; a cheat sheet; and `/embed` for iframes. Share links carry the program in the URL fragment. "Download for the CLI" exports the program, a `minab.config.json` and a `seed.sql`.
- Two small, backwards-compatible core changes, each with tests:
  - **`src/host/`**, extracted from `src/cli/`: `parseConfig` (the config shape without a file system), `FixtureExecutor`/`traced`/`DataSourceError`, and `formatSql`/`formatValue`. The CLI modules re-export them, so no caller changed. `test/host.test.ts` covers what only a file-less host sees.
  - **`EvalContext.onStatement(query, origin)`** in the interpreter. It's called just before each statement goes to the executor, with the AST node it was compiled from: the whole `Query`, or the pushed-down subexpression. This is what lets the playground's Execution tab highlight exactly which span of a rule became which SQL. Three cases were added to `test/evaluation.test.ts`.
- The playground has its own suite (`cd playground && npm test`, 126 tests):
  - every gallery example, record preset and tour lesson is run against the real engine and an in-process Postgres (a lesson's starter must *not* meet its goal, and its solution must);
  - the highlighter's keyword lists are diffed against the Langium-generated keyword union, so a grammar change can't leave a keyword uncolored;
  - DDL generation, share links, and the engine's editor intelligence (hover, completion, AST).
- **What running every example against a real database found:**
  - the `GROUPBY .customer.country` compiler gap ("Next job" above);
  - a confirmation that a rule's related rows are read through the record's primary key. A record with a new, unsaved id traverses to `null`, so the traversal examples validate existing orders.
  - The already-known bare-rule collection bug also bit two gallery ideas. The gallery uses the equivalent `COUNT(#Order[.customer == ^ AND …])`, which works.

  - the brief;
  - user flows;
  - per-screen state specs;
  - the design contract (tokens plus component props; engine, state and hooks are off limits);
  - ready-to-paste Claude Design prompts;
  - a launch kit.

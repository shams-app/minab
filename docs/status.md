## Current status

Roadmap Phase 0 (reconcile design history) and Phase 1 (grammar completeness & safety pass) are both done. Hamed supplied the complete v2 language design as two documents added to the Claude Project — `query-language-spec.md` (12 sections, `#alias` sigil, full type system, functions, `if`/`if!`/`switch`, loops, `INSERT`/`UPDATE`/`DELETE`) and `docs/showcase.md` (14 sections of runnable examples) — replacing the old pipeline-only spec wholesale, not just adding the five originally-flagged constructs.

Both are now in the repo as the authoritative spec/grammar/example set. `npm run langium:generate` and `npm run build` are clean; `npm test` is 49/49 green, rebuilt directly from `docs/showcase.md`'s own sections. Three genuine defects were found and fixed along the way (see the session log below for the full detail): a clause-order regression in the showcase's grouping example, a missing `vivify` flag on `CurrentRecord` (so `.doctor!.id = 21;` didn't parse), and a misuse of `isnot` as general inequality where `!=` was meant. No semantic services yet — no `ScopeProvider`, no `Validator`, no evaluator.

`docs/query-language-spec.md` is the spec; `docs/showcase.md` is the synced example corpus; `docs/roadmap.md` has the full phased plan (updated to match); `.cursor/rules/` carries the same working conventions into Cursor, updated for the v2 sigil/keywords/DML.

Roadmap Phase 2 (scope resolution) is now also done — see the 2026-09-14 log entry below. Sigil resolution (`.`/`^`/`#alias`/`KEY`) exists as a standalone service, not a Langium `ScopeProvider`, because Minab's tables/columns come from a schema the host application supplies at runtime, not from in-file declarations (there are none).

Roadmap Phase 3 (semantic validation) is now also done — see the 2026-09-16 log entry below. A Langium `Validator` (`src/language/minab-validator.ts`) catches 3 of the 4 originally-listed checks; the 4th (collection-vs-scalar) was deferred to Phase 4 with Hamed's sign-off, since it needs a real column-type representation that doesn't exist yet.

Roadmap Phase 4 (type system) is now also done — see the 2026-09-17 log entry below. `src/language/types.ts` and `src/language/minab-type-checker.ts` implement full type inference/checking over the expression grammar, picking up the collection-vs-scalar check deferred from Phase 3 and superseding the scope resolver's one-hop traversal bound with real arbitrary-depth `ref` chains and `collection` broadcast. Two genuine open findings in `docs/showcase.md` were surfaced (not fixed) and need Hamed's call — see that log entry.

## Next job

**Two small loose ends before the next roadmap phase**, both surfaced by Phase 4's verification pass and needing Hamed's call before touching `docs/showcase.md` (per spec-governance — findings get confirmed, not silently patched):
1. §10's `cancelledOrdersFor` example compares `.customer` (a `ref(Customer)`) directly against a `UUID` parameter — the type-checker rejects this under strict no-implicit-coercion. Is the fix `.customer.id == customerId` (a showcase typo, matching how every other example traverses through a ref), or should ref-vs-referenced-table's-key-type equality be a first-class allowed comparison (a real language-design question, since `schema.ts` has no "primary key" concept to hang that on)?
2. §11's "value-producing if branch" example assigns to a bare `total` never declared as a `let` in that fragment, while its condition reads `.total` (with the dot) — looks like a typo (`.total = .total + 100;`?) but hasn't been confirmed.

Once those are resolved, **Roadmap Phase 5 — Execution strategy + evaluator** is next: the biggest open architectural question in the roadmap (interpret vs. compile-to-SQL vs. hybrid). Start with the ADR under `docs/adr/` per `docs/roadmap.md` Phase 5's task list — this needs Hamed's sign-off before any implementation.

### 2026-09-16 — Phase 3: semantic validation

- Picked up the "Next job" note above. Investigated the four checks the roadmap listed and found two open design gaps before writing any code, both resolved with Hamed:
  - **`$` outside a field rule**: the spec (§6.2, line 374) says any `$` usage makes the whole program "implicitly a field-level rule" — there's no AST-level marker distinguishing "inside" vs. "outside" one, since a Minab program has exactly one top-level statement. Hamed's answer: `$` is valid *anywhere* in the program (any nesting — subqueries, loops, function bodies) as long as the host says up front this program is being run as a field rule; otherwise any `$` anywhere is an error. This is host-supplied context, not something derivable from the AST — same shape as `MinabSchema`.
  - **Collection-vs-scalar check**: `schema.ts`'s `MinabColumnSchema.type` is still a free-form display string (flagged provisional back in Phase 2), with no structured collection/scalar flag. Hamed's call: **defer this whole check to Phase 4** rather than bolt on a throwaway representation now that Phase 4 would just replace. Phase 3 therefore ships 3 of the 4 originally-listed checks.
- Implementation:
  - `src/language/schema.ts` — added `MinabRuleContext` (`{ isFieldRule: boolean }`) and `DEFAULT_RULE_CONTEXT` (`isFieldRule: false`), the host-supplied field-rule-context contract described above.
  - `src/language/minab-module.ts` — threaded `ruleContext` through as a new service and `createMinabServices` parameter (defaulting to `DEFAULT_RULE_CONTEXT`), exactly mirroring how `schema` is already threaded; added the call to wire up validation checks.
  - `src/language/minab-validator.ts` (new) — `MinabValidator` with three checks: `FieldValue` (checks `ruleContext.isFieldRule`), `GroupKeyRef` and `NamedScope` (both thin wrappers delegating to `MinabScopeResolver.resolveGroupKeyRef`/`resolveNamedScope` from Phase 2, reusing their existing `reason` strings as diagnostic messages verbatim — no new resolution logic needed for these two).
  - `test/validation.test.ts` (new, 7 tests) — first use of Langium's validation pipeline in this repo; used `validationHelper` from `langium/test` (confirmed present in the pinned Langium 4.4 version) rather than `parseHelper`, asserting on `result.diagnostics`. Caught one non-obvious typing issue this way: `tsc -b` (not `vitest`, which transpiles without full type-checking) flagged that a `Diagnostic`'s `message` is typed `string | MarkupContent`, not always `string` — added a small `messageText()` unwrap helper in the test file rather than casting.

### 2026-09-17 — Phase 4: type system

- Picked up the "Next job" note above. Given the size, planned first (a written plan, reviewed and approved before implementation): confirmed three design forks with Hamed up front — numeric literals (`100`/`12.5`) are untyped constants that unify with either INTEGER or DECIMAL with no `CAST` needed (only two already-*typed* values of different numeric bases need one); TEXT and CITEXT are interchangeable, unlike every other type pair; vivify (`!`) on a `collection` path step is enforced as a real diagnostic now, settling spec §12 item 17's "assumed but not separately confirmed" reading.
- Built the type representation (`src/language/types.ts`, new) and the type checker (`src/language/minab-type-checker.ts`, new — `MinabTypeChecker.typeOf`, a pure best-effort inference function, plus `registerTypeCheckingChecks`, a parallel set of Langium validation checks alongside Phase 3's `minab-validator.ts`, not merged into it). Updated `schema.ts`'s `MinabColumnSchema.type`/`MinabFunctionSchema` from Phase 2's provisional display-string types to the real structured representation, and added `MinabRuleContext.fieldType?` so `$` can be typed. Added one small additive method to `minab-scope-resolver.ts` (`resolveCurrentRecordScope`) so the type-checker can get a `.field` access's base table without changing any existing method's behavior.
- **Verification went beyond unit tests first**: before writing the formal suite, ran every one of `docs/showcase.md`'s 14 sections through the type-checker directly (a throwaway script). This caught and fixed four real defects in the implementation, each the kind of thing that's easy to get wrong reasoning abstractly but obvious once checked against real examples:
  1. `#Customer`/bare `FROM Order` (a `TableRef`/`NamedScope` opening a whole table) was typed as a single record instead of a collection — broke every `EXISTS(#Table[...])` and `FROM Table` pattern in the showcase.
  2. `SUM(.total)`/`AVG(.total)` after `GROUPBY` (spec §4.1: "`.` refers to a row within the current group") were rejected because the aggregate's argument wasn't literally collection-typed — the implicit per-group aggregation form needed its own rule, distinct from the explicit-collection form (`SUM(.orders.total)`).
  3. A bare function-call name (`SUM(...)`, `COUNT(...)`) is itself a `NameRef` node at the grammar level — the new unresolved-name check (added because deep `.field` traversal needs *some* way to surface a genuinely-wrong name, beyond Phase 2/3's existing checks) was flagging every built-in call as "unknown name" before it special-cased callee position.
  4. A `ListLiteral` assigned to a `JSON`-typed `let`, and `[N]`-style positional access through a `JSON` value, were both rejected — spec §7.3/§3.5 explicitly allow both, but the grammar's own documented ambiguity (§12 item 4: a literal `[N]` always parses as `TupleAccess`, never `FilterAccess`) meant the positional-access logic needed to live in `TupleAccess`'s check, not `FilterAccess`'s.
  - Also removed a check that didn't survive contact with the showcase: an initial "a program's bare top-level tail must be BOOLEAN" rule (reasoning that spec §6 makes a bare expression "a complete, executable rule") was wrong — several showcase sections end a top-level program in a non-boolean value for illustration (`sumEven`, `point[0] + point[1]`), and whether a program is actually being run as a validation rule is host-supplied context, the same shape as `ruleContext.isFieldRule` already is — not derivable from "the tail happens to be a bare expression."
  - `minab-scope-resolver.ts` also picked up one small, empirically-discovered extension: SELECT-item aliases are now registered in the scope stack, so `ORDERBY total_spent` (spec §4.1's own showcase §5 example, `SELECT ... SUM(.total) AS total_spent ... ORDERBY total_spent DESC`) actually resolves — this had never been exercised by any test before, since Phase 2's scoping suite didn't cover ORDERBY-referencing-a-SELECT-alias.
- **Two genuine open findings, flagged rather than silently resolved** (per spec-governance — `docs/showcase.md` isn't touched without confirmation): §10's `cancelledOrdersFor` compares `.customer` (`ref(Customer)`) directly against a `UUID` parameter, which strict no-implicit-coercion rejects — probably a showcase typo for `.customer.id == customerId` (matching every other ref-traversal example), but could instead be a real design question about ref-vs-key-type equality, and `schema.ts` has no "primary key" concept to hang that second reading on anyway. §11's "value-producing if branch" example assigns to a bare `total` never declared as a `let` in that fragment, while its own condition reads `.total` — looks like a typo (`.total = .total + 100;`?). Both are now the top of the next job list.

- `test/type-checking.test.ts` (new, 37 tests) — one `describe` block per rule category (let/assignment type-checking, numeric-literal flexibility, TEXT/CITEXT interchangeability, deep ref traversal, the collection-vs-scalar boundary, null-as-operand rules, if/else typing, vivify-on-collection, user/built-in function calls, `$` typing, assignment targets, GROUPBY/KEY typing including a SELECT-alias-from-ORDERBY case).

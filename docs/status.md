# Minab — Status

A running note of where things stand and what to do next. Update the top two sections every session; add a new dated entry to the log at the bottom rather than editing old ones.

## Current status

Roadmap Phase 0 (reconcile design history) and Phase 1 (grammar completeness & safety pass) are both done. Hamed supplied the complete v2 language design as two documents added to the Claude Project — `query-language-spec.md` (12 sections, `#alias` sigil, full type system, functions, `if`/`if!`/`switch`, loops, `INSERT`/`UPDATE`/`DELETE`) and `docs/showcase.md` (14 sections of runnable examples) — replacing the old pipeline-only spec wholesale, not just adding the five originally-flagged constructs.

Both are now in the repo as the authoritative spec/grammar/example set. `npm run langium:generate` and `npm run build` are clean; `npm test` is 49/49 green, rebuilt directly from `docs/showcase.md`'s own sections. Three genuine defects were found and fixed along the way (see the session log below for the full detail): a clause-order regression in the showcase's grouping example, a missing `vivify` flag on `CurrentRecord` (so `.doctor!.id = 21;` didn't parse), and a misuse of `isnot` as general inequality where `!=` was meant. No semantic services yet — no `ScopeProvider`, no `Validator`, no evaluator.

`docs/query-language-spec.md` is the spec; `docs/showcase.md` is the synced example corpus; `docs/roadmap.md` has the full phased plan (updated to match); `.cursor/rules/` carries the same working conventions into Cursor, updated for the v2 sigil/keywords/DML.

Roadmap Phase 2 (scope resolution) is now also done — see the 2026-09-14 log entry below. Sigil resolution (`.`/`^`/`#alias`/`KEY`) exists as a standalone service, not a Langium `ScopeProvider`, because Minab's tables/columns come from a schema the host application supplies at runtime, not from in-file declarations (there are none).

Roadmap Phase 3 (semantic validation) is done — see the 2026-09-16 log entry below. A Langium `Validator` (`src/language/minab-validator.ts`) catches 3 of the 4 originally-listed checks; the 4th (collection-vs-scalar) was deferred to Phase 4 with Hamed's sign-off, since it needed a real column-type representation that didn't exist yet.

Roadmap Phase 4 (type system) is now also done — see the 2026-09-17 log entry below. A real structured type representation (`src/language/minab-types.ts`) replaced `schema.ts`'s free-form column-type string; a new `MinabTypeChecker` (`src/language/minab-type-checker.ts`) infers types over the full expression grammar; and `MinabValidator` now enforces no-implicit-coercion, the §3.4 collection-vs-scalar boundary (the check deferred from Phase 3), and the §7.7 null-operand rules. Two spec §12 open questions blocking this phase (built-in/`&`-prefixed function disambiguation, item 10; what a query-tailed function's return type means, item 11) were resolved with Hamed and written up in the spec (§5.3/§5.3.1, §8.6). One real defect was found empirically in four worked examples (comparing a `ref` field directly against a scalar) and fixed in both the spec and showcase — see the log entry for detail.

Roadmap Phase 5 (execution strategy + evaluator) is now also done — see the two 2026-09-17 log entries below. `docs/adr/0001-execution-strategy.md` chose the hybrid and was signed off; `src/language/minab-sql-compiler.ts` compiles the relational layer to parameterized SQL, `src/language/minab-interpreter.ts` evaluates everything else against the record the host holds, and the interpreter pushes the smallest table-touching subexpression down to the compiler. Minab can now actually *run* a pipeline query and a correlated validation rule, not just parse, scope, validate, and type them.

## Next job

**Finish the execution layer, then Roadmap Phase 6 — CLI / runner.** Phase 5 shipped the strategy and a real evaluator for queries and validation rules, but three things it deliberately left out are now the natural next increment, each currently failing with an explicit "not executed yet" reason rather than a wrong answer: **loops** (§9.4), **`INSERT`/`UPDATE`/`DELETE` execution** (§10 — ADR 0001 already settles *how* they execute, relational targets compiling to SQL DML and `JSON`-array targets staying interpreted; building it is what's left), and **`.$index`** (§3.5). Worth doing before Phase 6, since a CLI that can't run a write is a thin thing to ship.

Two things also want a real Postgres behind them rather than a fixture executor: the generated SQL has only ever been diffed against hand-written expected SQL, never executed, and `CITEXT` case-insensitivity is asserted in the interpreter but assumed in the compiled path. See `docs/roadmap.md` Phase 6 for the CLI task list itself.

### 2026-09-17 — Phase 4: type system

- Picked up the "Next job" note above. Two spec §12 open questions were flagged as blocking before any code got written, resolved with Hamed:

It's now also covered for real: `test/sql-compilation.test.ts` compiles that exact example.
  - **The ADR's DML claim was too broad.** It said "every DML form in §10 already names a single target table per statement" — but §10 explicitly allows a `JSON`-array field as a target, which is not a table at all, and §3.5 confirms the ordinal DML forms (`DELETE .customers[2]`, `WHERE .$index > 2`) are *only* legal against a `JSON`/`T[]` source. Rewrote that section to split relational targets (SQL DML) from `JSON`-array targets (interpreted read-modify-write), which lands on the same seam as the rest of the ADR.
  - **The ADR silently assumed a SQL dialect where the spec deliberately doesn't.** §7.2 calls the type vocabulary "storage-agnostic"; the ADR emits Postgres-flavored SQL. Not a contradiction (a compilation target isn't a type mapping) but worth stating, so a consequence now records it, notes `IS [NOT] DISTINCT FROM` is standard SQL rather than Postgres-only, and names the per-dialect equivalents. Also added the `CITEXT` consequence: compiled against a real `citext` column equality is case-insensitive for free, so the *interpreter* has to match that deliberately or the two runtimes silently disagree.
  - One citation fix (implicitly-async `fn` is stated in §8's preamble, not §8.1).
- Implementation, per the ADR's own "Phase 5 implementation scope":
  - `src/language/minab-sql-compiler.ts`, `src/language/minab-interpreter.ts`, `src/language/minab-executor.ts` — see `docs/roadmap.md` Phase 5's "What actually shipped" for the full breakdown. Both services wired into `minab-module.ts` alongside the existing four; the host's connection and the record under evaluation are passed per call to `interpreter.evaluate`, not baked into `createMinabServices`, since they're per-invocation rather than per-embedding.
  - `src/language/schema.ts` gained `foreignKey` (on `ref`/`collection`) and `primaryKey` (on a table). This was forced by implementation, not planned: Phases 2-4 only ever needed to know *what* a traversal lands on, but executing one needs to know *how* — `.customer.country` is a join, `COUNT(.orders[...])` a correlated subquery, `. != ^` a comparison of row identities. Both optional, so existing hosts/fixtures keep working and an undeclared relation fails with an explicit reason rather than guessing at a naming convention. Also closes the primary-key gap Phase 4 flagged when it found the four `ref`-compared-to-scalar defects.
- Three judgment calls worth a second look, each documented where it lives:
  - **`ref` traversal compiles to a correlated scalar subquery, not a join.** Chosen for §7.7 rule 1: traversal through a null `ref` must evaluate to `null`, and an inner join would drop the row instead. A `LEFT JOIN` would also work but has to be hoisted into the `FROM` clause; the subquery is local to the expression and a planner can usually flatten it.
  - **The pushdown boundary is the *smallest* table-touching subexpression, not the largest compilable one.** The compiler can bind local values as parameters, so it would happily swallow a whole rule — but `COUNT(.orders) < 5` pushed down whole compiles the `5` to a bare placeholder, leaving SQL comparing two untyped parameters (which real Postgres rejects). Pushing down the smallest node that actually needs the database keeps every generated statement grounded in real columns, and keeps the operators themselves under the interpreter's null/`CITEXT` rules.
  - **A user-written `==` compiles to `IS NOT DISTINCT FROM` even in a `JOIN ... ON`**, which reads oddly for a join but is what §7.7 literally says. The compiler's *own* synthesized join predicates are the opposite case and stay plain `=`, so a null FK matches nothing.
- Two gaps the end-to-end tests caught that the SQL-diff tests alone would not have: `$` had no compiled form at all (a field rule's `EXISTS(#Customer[.id == $])` failed), and a relation reached off the *outer* record rather than a query scope wasn't recognized as a collection (`COUNT(.orders[...])` at the top of a rule). Both fixed. A third was a masking bug — a genuine failure inside a real collection (an undeclared foreign key) was being swallowed and re-reported as the generic "that isn't a collection", which is exactly the kind of message that wastes someone's afternoon; the structural check now runs first so the real reason survives.

# X1 Queries accept `switch`, `if`, `is` and JSON literals

Status: done
Date: 2026-10-02
Branch / PR: sema/brave-brown-0b3ul0

## Done
A query can now use `switch`, `if`, `is`/`isnot` and JSON literals, and `FROM` can start from a filtered related collection. All of it compiles to SQL and runs on Postgres (PGlite).

- `switch` and `if` become `CASE`. A `null` case value makes a searched `CASE` (`IS NULL`). No `else` gives `ELSE NULL`. A block with only a tail is its tail. A block with statements refuses with the new code `compile.blockInQuery`.
- `is null` / `isnot null` become `IS [NOT] NULL`. The five JSON kinds use `jsonb_typeof(x) IS [NOT] DISTINCT FROM 'kind'`, so a `null` is "not that kind", as in the interpreter.
- JSON object and list literals become `jsonb_build_object` and `jsonb_build_array`. Keys and values are bound parameters with a type (`$1::text`, `$2::numeric`).
- Text and number literals in `CASE` results and JSON literals carry a type. Bare parameters made Postgres read them as text.
- `FROM .orders[...]` compiles to `FROM "Order" AS _rN WHERE <fk> = <outer key> AND <filter>`. A plain `FROM .orders` (no filter) refused before; it works now too.
- `compile.blockInQuery` is in the registry (new area `compile`). `SqlResult` failures carry `code` and `params` when the refusal has a code.
- Tests: expected SQL in `test/sql-compilation.test.ts`; Postgres runs in `test/queries/cases/x1-expressions.cases.ts` (12 cases); scalar cases in `test/differential/cases/x1-expressions.cases.ts` (24 cases). The C1 known gap "is null has no SQL form" is removed (fixed).

Differences from the card, noted here:
- **Grammar change (approved by the owner in this session, 2026-10-02).** The card's `FROM .orders[.status == "x"]` did not parse: `FromSource` allowed no filter. I changed `FromSource` in `src/language/minab.langium` to accept an optional `[filter]` after `.field`, and updated spec §4.2 (FROM item) and §11 (grammar). No new tokens, so the tokenizers need no change. `langium:generate` prints only the known warning.
- **Scope resolver.** `FROM .orders` at the top of a rule did not find its table, so `check` failed. `MinabScopeResolver` now takes the rule's `recordTable` for that one case (`minab-module.ts`, `minab-scope-resolver.ts`).
- **Parameter numbers.** For `FROM .orders[...]` the source parameters are bound before the SELECT list, so `$n` is not in text order in that one form. A `switch` arm with several values repeats its result, so `$n` stays in text order.
- Test support: the query harness takes an optional `record` (and the schema loader a `recordTable`); JSON values compare with sorted keys (jsonb does not keep key order).
- No playground content said these constructs fail in a query, so none changed.

## Later
- `x is null` on a `JSON` column that holds the JSON value `null`: the interpreter says true, SQL says false (`jsonb 'null'` is not SQL null). The compiler has no column types, so it cannot tell — C5 or a typed-compiler card.
- `is array` and the other kinds on a non-JSON column fail in Postgres (`jsonb_typeof` needs jsonb). The spec calls this meaningless, and `check` does not reject it — a checker rule — next card.
- A bare literal as the operand of `is`/`CASE` subject (`"a" is string`) has an untyped parameter — typed literal parameters (see the C1 Later item) — C2 or next card.
- Add a `docs/showcase.md` example for `FROM .orders[filter]` — prose, not needed for done — G1.

# L6 Date and time built-ins

Status: done
Date: 2026-10-03
Branch / PR: sema/awesome-ritchie-w04pzq (pull request: see the branch)

## Done
`NOW`, `TODAY`, `YEAR`, `MONTH`, `DAY`, `HOUR`, `MINUTE`, `DATE_ADD`, `DATE_DIFF` and `CAST(datetime AS DATE|TIME)` work in the interpreter and in SQL, with the run's time zone. They give the same answer on PGlite in `UTC`, `Asia/Tehran`, `Europe/Berlin` and `America/New_York`, including daylight-saving days.

- **Calendar code.** `src/language/dates.ts` (new): days from a civil date and back, month clamp, ISO parsing, `Intl.DateTimeFormat` offsets per instant, and the local-time rule (a time that does not exist, or exists twice, is read as standard time, like Postgres — I checked this on PGlite).
- **Table.** `minab-builtins.ts` has the nine functions. New parameter kinds `datish`, `timeish` and `unit`. `evaluate` gets the run's clock; `sql` gets a `SqlClock` whose `now()` and `zone()` bind parameters. A unit argument is read from the text literal and is not a SQL parameter.
- **Checker.** The unit must be a text literal from the list for the first argument (`DATE`: year, month, week, day; `DATETIME` adds hour, minute, second). Else `call.unknownDateUnit` (new code, in the registry and in `docs/reference/diagnostics.md`).
- **Interpreter.** The clock is read once for each run (default: system time, `UTC`) and passed to built-ins, casts and the compiler. A `DATETIME` read from the data port or the record becomes an ISO 8601 UTC text with milliseconds (`normalizeIn`), so `.paid_at < NOW()` compares instants.
- **SQL compiler.** `compileQuery` and `compileValue` take an optional clock. `NOW()` and `TODAY()` are `$n::timestamptz` and `AT TIME ZONE $n::text`, never `now()`. Without a clock (the `compile()` preview) the system time in `UTC` is bound. `CAST(datetime AS DATE|TIME)` uses `AT TIME ZONE`.
- **Tests.** `test/differential/cases/l6-dates.cases.ts` (126 cases), `test/dates.test.ts` (20 tests: calendar code, the clock, the SQL text, checks). The differential harness got a `clock` field, neutral `DATE`/`TIME`/`DATETIME` defaults, and it now builds the services with the record's table (as a real run does) when a case has a record. `sameValue` treats two date-time texts of one instant as equal. Mutation checks: SQL `now()`, the daylight-saving rule, the unit check and the `DATETIME` reading each broke at least one test when undone.
- **Follow-up (owner asked for it after the first PR).** `CAST(text AS DATETIME)` and `CAST(date AS DATETIME)` now give an instant too. A zone in the text is used; without one the text (or the date, at midnight) is read in the run's time zone. In SQL: a `CASE` on a zone pattern, `timestamptz` with a zone and `timestamp AT TIME ZONE` without one. `breaking: true` in `changes/L6-2.md`. Four C3 expectations and two `test/casts.test.ts` rows changed on purpose (the old answer was `2026-10-02 08:30:00` text). 13 new differential cases.
- **Docs.** Spec §5.3.1 (date functions), §7.2 (what `DATETIME` is, the run's time zone, JSON forms), §5.5 (cast rows). Showcase section 18 (three blocks, added to `test/spec-examples.test.ts`).
- **Playground.** Hover docs, highlight names and three cheat sheet entries.

Differences from the card, noted here:
- `DATETIME` is held as an ISO 8601 UTC **text** inside the interpreter, not as a number of milliseconds. It leaves Minab in the same form, and the text sorts like time, so the existing comparison code works without a type switch. `dates.ts` converts to milliseconds for every calculation.
- The `DATE_DIFF` rule at a month end is "the day (and time) of `a` has reached that of `b`", so Jan 31 to Feb 28 is `0` months. It is simple to write in SQL and in the interpreter and both agree. D21 says only "whole units, truncated toward zero".
- Existing test `test/builtins.test.ts` lists the names in the table; I added the nine names on purpose.

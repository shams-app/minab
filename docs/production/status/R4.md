Status: done

## Done
A run now stops at its limits and can be cancelled. Every failure of `prepare`, `compile` and `run` is a structured error with a stable code from the registry, an English message, a source range and params. A host can map it to an HTTP status or an editor marker without parsing text.

- `src/runtime/limits.ts` (new): the `Limits` of D36 with their defaults, `resolveLimits` (host), `tightenLimits` (a run takes the smaller value, so it never raises a limit), and `RunBudget`. The budget counts statements, rows, loop iterations and call depth. It joins the host's `AbortSignal` and the wall-time timer into one signal. `check()` is called between interpreter steps. `race()` stops waiting for a port call when the run is aborted, so a host function that ignores the signal still ends on time.
- `src/runtime/errors.ts` (new): `runError` (builds an error from the registry), `sqlstateOf`, `dataFailure`.
- `prepare`: `limit.sourceTooLong` (UTF-8 bytes, before parsing) and `limit.tooDeep` are error diagnostics. A program they stop has one diagnostic; `run` and `compile` refuse it. A bracket scan runs before the parser (see Questions).
- `run`: `{ ok: true, value, logs, stats: { statements, rows, durationMs } }` or `{ ok: false, error: { code, message, range?, params } }`. `run(…, { signal, limits })`. A signal that is already aborted gives `cancelled` before any port is called.
- `compile()` gives `{ ok: true, sql }` or `{ ok: false, error }`.
- Codes in the registry (and `docs/reference/diagnostics.md`, regenerated): `cancelled`; `limit.callDepth`, `sourceTooLong`, `timeout`, `tooDeep`, `tooManyIterations`, `tooManyRows`, `tooManyStatements`; `data.error`, `data.noPort`; `eval.failed`, `hostFunctionFailed`, `hostFunctionMissing`, `missingInput`, `programInvalid`, `writesNotSupported` (the last three already existed as plain strings); `compile.notSql`, `nothingToCompile`, `programHasErrors`. `eval.divisionByZero` came with C4. Every other failure of the interpreter is `eval.failed` (`params.reason`), and of the compiler `compile.notSql`.
- `range`: the innermost failing expression sets it (a failing `CAST` points at the `CAST`).
- Data errors: `22012` is `eval.divisionByZero`, `22P02` and `22003` are `eval.castFailed`, anything else is `data.error`. `params.sqlstate` is set when the driver error has a SQLSTATE. Neither the SQL text nor the driver's message is copied. A host function that throws is `eval.hostFunctionFailed`, also without its text.
- Compatibility adapter: `MinabInterpreter.evaluate` stays as the old entry for the CLI and the playground. It is `@deprecated`, calls the new `run`, gives the old result shape, throws a data port failure again, and has no limits. **Remove it in R8, or in whichever of R7 and R8 merges last.**
- Docs: `src/runtime/README.md` (result and error shapes, the limits table, cancellation), `scripts/diagnostics-doc.mjs` (areas `limit`, `data`, `cancelled`).
- Tests: `test/limits.test.ts` (36), `test/run-errors.test.ts` (27, three of them on PGlite with real SQLSTATEs).

## Questions for the owner
- **Breaking change** (before 1.0, allowed by D38; the fragment says `breaking: true`). `run` returns `logs` and `stats`; `compile` returns `sql` where it returned `query`; a data port failure is now a result (`data.error`) and no longer a rejected promise. Recommendation: keep.
- **Code names.** I used the names of the card (`limit.timeout`, `limit.tooManyRows`, …). ADR 0002 section 5 has other examples (`limit.time`, `limit.rows`). Recommendation: fix the ADR text when R6 or G1 touches it.
- **A failed run has only `error`**, as the card says. The ADR also puts `logs` and `stats` on a failure. Recommendation: add them when L7 builds logs.
- **Bracket scan before the parser.** The card says nesting is checked at `prepare`. The parser needs more than linear time and stack for deep programs: some shapes run out of stack at about 80 levels, and a 30,000-level source used over 8 GB before the walk of the tree could run. So `prepare` first scans the brackets in one pass (text in strings, quoted names and comments does not count) and refuses a source whose brackets nest deeper than `nestingDepth`. The walk over the expressions still runs after parsing. When the parser itself runs out of stack below the limit, `prepare` reports `limit.tooDeep` and `params.used` is a lower bound (`limit + 1`). Recommendation: keep.
- **Size.** About 15 hand-written source and test files, and about 1,500 changed lines with the tests (budget 12 files and 1,000 lines). Within twice the budget, so I did not stop.

- Parse time and memory grow faster than the size of a deeply nested source. The bracket scan caps the damage at the `nestingDepth` limit, but a program at the limit still costs the parser time. Measure it and set the budget — Q3 (performance).

## Questions for the owner
Why the card does not fit:

1. **The engine is not a thin wrapper.** `playground/src/engine/engine.ts` (495 lines) owns the per-host runtime, the syntax tree, the Execution tab trace, the `Database` (table preview, SQL console, reset, seed SQL), editor intel and snippet runs. `createWorkerMinab` offers only `prepare`, `compile`, `run`, `complete`, `hover`, `signatureHelp`.
2. **Ports are fixed per worker.** `serveMinab(self, { ports })` takes one set of ports for the worker. The playground needs a data port and an event sink for each run (the tracer needs the syntax tree of that run to name the node of each statement). The trace and the SQL columns also cannot cross the bridge: `DataPort.execute` returns rows only.
3. **`createWorkerMinab` is bound to one schema.** The playground changes host (schema) all the time, so the client would rebuild it on every `setHost`.
4. **Double work.** If the client runs through the bridge, the bridge runtime parses and checks the program, and the engine parses it again for the tree, the trace and `describeProgram`. Two runtimes per host, two parses per run.
5. **`database.ts` cannot become `createPgliteDataPort`.** The port has no column names, no `exec` results and no table preview. Only about 15 lines of boot code are shared.
6. **Tests.** The 140 playground tests drive `Engine` directly. They do not cover worker or client, so a rewrite there is checked only by build and by hand.

Recommendation: add a small card before H7 (owner decision, touches `src/browser/`, which H7 may not edit). It would give the browser entry (a) a data port and an event sink that can be chosen per run, (b) a data port result with column names, and (c) a hook that gives a prepared program's syntax tree or trace to the host. Then H7 becomes the thin change its card describes. Other option: shrink H7 to "use the shared worker bridge types and `createPgliteDataPort` where they fit" and accept `partial`.

# C9 Null and `IN`: one answer in both runtimes

Status: done
Date: 2026-10-12
Branch / PR: claude/c9-null-in

## Done
When a value is `null` at run time, the interpreter and Postgres now give the same answer (D46 option a, spec §7.7). No `knownGap` case is left: `test/differential/cases/c1-known-gaps.cases.ts` is deleted.

- **Arithmetic (Build 1).** In the interpreter, `+ - * / % \` and unary `-` give `null` when an operand is `null`. This comes before any other check, so `null / 0` is `null`. Postgres already answered `null` (`divisionSql` and `wholeDivisionSql` use strict functions, so `div(NULL, 0)` is `NULL`, no error). The checker already typed the result as nullable: no change there.
- **Ordering and `LIKE` (Build 2).** The interpreter returns `false` for a `null` side. The compiler wraps `<`, `<=`, `>`, `>=` and `LIKE` in `COALESCE(…, FALSE)` when a side can be `null`. It keeps the plain form in a "truth position": the condition of a `WHERE` (also in `UPDATE`/`DELETE`), `HAVING` or a filter `[...]`, reached only through `AND` and `OR`. Under `NOT`, `==`, `if`, a function, or in `SELECT`, the `COALESCE` form is used. A side counts as "not null" only when that is sure: a literal, a non-nullable column of the current row, and arithmetic over those. The literal `null` next to these operators is still the check error `null.orderingWithNull` / `null.likeWithNull`.
- **`IN` (Build 3).** SQL `IN` never gives `NULL` now. A list is `(v IS NOT DISTINCT FROM a OR v IS NOT DISTINCT FROM b)`; a subquery is `EXISTS (SELECT 1 FROM (<subquery>) AS "_in"("v") WHERE "_in"."v" IS NOT DISTINCT FROM v)`. The plain `v IN (…)` stays when no side can be `null`, or in a truth position when the value and the items are not both nullable. The `CITEXT` casts of D15 are kept. In the list form the value is repeated: that is safe, because every Minab expression compiles to SQL with no side effect and no volatile function (the clock is a bound parameter, D21), and a parameter is the same `$n` again. In the subquery form the value is written once.
- **`IN` with a subquery in the interpreter (Build 4).** The subquery runs as one statement, and its one column gives the list of values, with the same `==` rules as a list (`subqueryValues` in `minab-interpreter.ts`).
- **A JSON `null` is `null` (Build 5).** For a `JSON` operand, `is null`, `isnot null`, `==` and `!=` read a JSON `null` as SQL `NULL` (`NULLIF(x, 'null'::jsonb)`), as the interpreter already did.
- **Sweep (Build 6).** Cases for `switch` and `if` on a `null`, a `COALESCE` chain, `MIN`/`MAX`/`SUM`/`AVG` over only nulls, and `ORDERBY` on a nullable column (nulls last). All agree; nothing needed a fix.
- **Tests.** `test/differential/cases/c9-null-rules.cases.ts` (58 cases, each with `expect`), `test/queries/cases/c9-in.cases.ts` (13 query cases: `WHERE` on a nullable column with and without `NOT`, `IN` and `NOT IN` with a list and a subquery, `ORDERBY`), and five SQL-text tests in `test/sql-compilation.test.ts` that show both forms (plain in `WHERE`, `COALESCE` / `IS NOT DISTINCT FROM` / `EXISTS` elsewhere).
- **Docs.** Spec §5.1 (two `null` rows in the operator table), §5.6 (a JSON `null` is `null`), §7.7 (a new part "A `null` value at run time", with D46's example). Showcase §7: one `COALESCE` example at the end of the section, so no block numbers move.

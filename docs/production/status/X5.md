# X5 Writes, part 1: the write port and table writes

Status: done
Date: 2026-10-04
Branch / PR: sema/sweet-planck-tpr2fh

## Done
`INSERT`, `UPDATE` and `DELETE` on tables run as parameterized SQL, in one transaction per run. A host must choose `writes: 'dry-run'` or `'apply'`. The CLI is a dry run unless you give `--apply`. A validation rule cannot write.

- **Write port** (`src/runtime/ports.ts`, `src/node/`): `pgWritePort(clientOrPool)` does `BEGIN` / `COMMIT` / `ROLLBACK`; a pool lends one connection for the whole run and drops it if the rollback fails. `queryFunctionWritePort(query)` is for a host that already has a transaction (TypeORM): it opens none, the host commits or rolls back. The row count is read from the shapes that `pg` and TypeORM give.
- **One run = one transaction** (`minab-interpreter.ts`): an applied run is wrapped in `write.transaction`. Reads in the run use the same transaction, so they see the run's writes. Any failure rolls everything back. `stats.writes` (`statements`, `rows`) and `writes: { mode, statements }` are in the run result. Writes count toward `limits.statements`.
- **Compiler** (`minab-sql-compiler.ts`, `compileWrite`): `INSERT` of an object, a list of objects (a missing key is `DEFAULT`), a table, a filtered table or a query (columns match by name; `SELECT .` means the whole row); `UPDATE` with `:` `+:` `-:` `*:` `/:` `:|` (`+:` joins text or adds numbers by the column type); `DELETE`. `ORDERBY`/`LIMIT`/`OFFSET` use a key subquery. Relation targets (`.orders`) get the foreign key condition, and `INSERT .orders` sets the link column. Everything is bound as a parameter.
- **Rules cannot write**: `rule.writeInRule` for `INSERT`/`UPDATE`/`DELETE` and for a record path assignment in a record rule or a field rule.
- **Checker**: a write target must be a table (`compile.writeTarget`), columns must exist and be plain columns (`compile.writeColumn`), values must fit the column type (`type.assignMismatch`), `SET {}` is an error (`compile.writeEmptySet`). New run error `eval.writeModeMissing`, checked before any port is called.
- **Scope fix** (`minab-scope-resolver.ts`): in the `WHERE`, `ORDERBY`, `LIMIT` and `SET` of `UPDATE` and `DELETE`, `.` is now a row of the target. Before, it meant the enclosing record, so `DELETE #Order WHERE .total > 1` did not check.
- **CLI**: `--apply` (needs `--database`; without it the error is exit 2). Dry run prints `dry run: N statements, nothing written (use --apply to write)` and each statement with its parameters, as D26 shows. `--json` prints `{ value, writes }` when the program writes, and the plain value otherwise.
- **Examples**: `order-dml` is now a `run` example; its `expected.json` shows the dry-run output. `reconcile-overdue-accounts` is a `run` example too (see Later: it was not in the card, but its check-only test could not stay).
- **Playground**: writes run as a dry run. The Execution tab lists them in order with a "dry run" badge (new event `dryRun`); table writes left `CHECK_ONLY`; gallery, cheat sheet and README notes updated.
- **Spec §10.4** "How writes run" (targets, one statement each, transaction, dry run, rules cannot write). No syntax change.
- Tests: `test/writes.test.ts` (35 cases, PGlite or Postgres) and updates to the tests that said "writes are not executed yet".

## Later
- Root `README.md`: the example table still marks `order-dml` and `reconcile-overdue-accounts` "check-only", and the CLI section does not mention `--apply`. The file is protected for this card — G1 (docs)
- A value in `SET` or `VALUES` that the compiler cannot express (a call to a host function, a user function that is not inlinable) fails with `compile.notSql`. The interpreter could evaluate it and bind the result — lane X
- In a dry run, a read after a write does not see the write (nothing ran). It is documented in the spec note, but a loop that depends on its own writes behaves differently in the two modes — lane X (document in the embedding guide, G2)
- Parameter numbers in a write are not in text order (`SET … = $2 … WHERE … = $1`), because the target filter is compiled first. It is valid SQL; only the readability of the dry run suffers — lane X
- `INSERT` into a table with a `ref` column cannot name the relation, only its foreign key column (`customer_id: …`) — next card (X6 or a later write card)

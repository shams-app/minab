# X2 Multi-key `KEY` and user functions inside a query

Status: done
Date: 2026-10-04
Branch / PR: sema/wizardly-planck-3irbym

## Done
`KEY.<name>` works when `GROUPBY` has several keys, and a simple user function can be called inside a query. Any other user function in a query is a `check` error. Both follow D22 and D23.

- **Multi-key `KEY` (D22).** A key is named by `AS name`, else by the last field of a plain path. `KEY.<name>` works in `SELECT`, `HAVING` and `ORDERBY`. A computed key with no name is `query.unnamedGroupKey`. A bare `KEY`, or a name no key has, is `query.keyNeedsName`. Implicit names that repeat are `query.duplicateGroupKeyName`. One key is unchanged.
- **Inlining (D23).** The compiler copies the body of a user function into the SQL and puts the arguments in place of the parameters. It works only inside a query. A call outside a query still goes to the interpreter. A function that cannot be copied is `query.functionNotInlinable`, with the reason (statements, recursion, host function, query). `check` reports it; the compiler refuses with the same code.
- **Group keys are compiled once.** `GROUP BY` and `KEY` now share the same SQL text and parameters. Before, a computed key (`.total + 1`) used in `SELECT` through `KEY` had its own parameter, and Postgres refused the statement ("must appear in the GROUP BY clause"). This also fixes it for one key.
- Shared rules live in `src/language/minab-query-inlining.ts`. The checker, validator and compiler all use it.
- Spec §2.2, §4.1 (item 4) and §8.4; showcase §5 (two blocks) and §10 (the call example now uses a simple function; one error block added); playground cheat sheet; `docs/reference/diagnostics.md` regenerated.
- Tests: `test/query-keys-functions.test.ts` (14: check codes and SQL text), `test/queries/cases/x2-multikey-functions.cases.ts` (7 cases on Postgres), three new codes in `test/diagnostic-codes.test.ts`, two showcase blocks in `test/spec-examples.test.ts`.

Differences from the card, noted here:
- **A third new code, `query.keyNeedsName`.** The card names two codes. A bare `KEY` over several keys (and `KEY.nope`) also needed a check error, or `check` would pass what `compile` refuses.
- The card says "interpreted = compiled". A user function inside a query has no interpreted form (the query always runs as SQL), so there is no differential case. The rows are checked on Postgres instead.
- Old tests changed on purpose: the "user function is refused in a query" tests in `test/sql-compilation.test.ts`, `test/ports.test.ts` and `test/run-errors.test.ts` now use the cases that are still refused (a function with a `let`, or a call outside a query). Showcase §10 #2 called `discountedTotal` (it has a `let` and a query) in a query; that is now an error by D23, so it is an error block and a simple function replaces it.

- A bare `KEY` over several keys has no record value in `SELECT` — D22 says "record", but only `KEY.<name>` can be read. A JSON object of the keys would need a design answer — post-1.0.

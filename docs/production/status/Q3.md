## Done
A program written by an end user is now tested against a crash, a hang, SQL injection, reads outside its schema and log forging. The tests found two real bugs. Both are fixed, each with a test that fails without the fix. `SECURITY.md` and `docs/security.md` are new.

- **Bug 1 (`LIKE`).** A pattern with thousands of `%` (for example `"%a"` repeated 20,000 times) overflowed the stack inside `run` with a `RangeError`: an uncaught exception, not a coded error. `likeMatch` in `src/language/minab-interpreter.ts` is now iterative (no recursion, no regex). Same answers as before, including the Postgres rule for a trailing `\`. Its time is at most the text length times the pattern length. The hard patterns of the card (`%a%a%a%a%a%a%b` on 10,000 characters) take about 1 ms.
- **Bug 2 (prefix operators).** `prepare` hung (minutes, and growing memory) on `-` or `NOT ` repeated 5,000 times. R4's bracket scan did not count them. `bracketDepth` in `src/runtime/prepare.ts` now also counts a run of prefix operators (`-`, `+` after an operator, `NOT`) as nesting, so it is `limit.tooDeep` before the parser starts. A binary minus does not count.
- **Fuzz tests** (`test/fuzz/`, with README, `fast-check`, fixed seed `20261004`, `MINAB_FUZZ_SEED` and `MINAB_FUZZ_RUNS`, 2,000 cases for each property when `CI` is set): `prepare` never throws and ends in under 200 ms (random tokens, random text, mutated spec/showcase/example programs, and the unmutated corpus); `run` on PGlite with tight limits always ends with a value or a coded error, in wall time plus 50 ms (arithmetic, comparisons, `IN`, `LIKE`, aggregates over one relation).
- **Prepare-time limits.** R4 already added `limits.sourceLength` and `limits.nestingDepth` (the names of D36, not `maxSourceLength` and `maxNesting`). `test/security/prepare-limits.test.ts` proves a 5,000-level program (brackets, calls, lists, `-`, `NOT`) and a 1 MB source give a coded diagnostic and no stack overflow.
- **SQL injection** (`test/security/sql-injection.test.ts`, PGlite): `"`, `'`, `;`, `--`, backticks, backslashes and Unicode in table names, column names, `sqlName` and string values. A `victim` table survives, and no value is ever in the SQL text.
- **Schema is the read surface** (`test/security/schema-surface.test.ts`): `#Secret`, `FROM Secret`, a join and an unknown column are scope errors, and the data port is never called.
- **NestJS** (`test/nestjs/security.test.ts`, in that folder because it is compiled with the decorator options): the schema comes from `schemaLoader`, never from the client; source text is refused (also when it comes next to an id); a batch over the limit runs nothing; error bodies hold no SQL, driver message or stack; the logger is off in production, escapes every kind of line break and respects the cap. H2 already had tests for much of this; these state the claims in one place.

## Questions for the owner
- **Parse time of deep programs.** A program just under the nesting limit still costs the parser a lot: `ABS(` nested 100 times takes about 1 s to prepare, and 200 times about 3 s (it grows faster than linear). Prepare is not interruptible. Hosts should prepare stored programs when they are saved (written in `docs/security.md`). Recommendation: lower the default `nestingDepth` from 200 to about 64 (D36 says 200, so this is your call), or ask a lane R or Q4 card to find the slow rule in the parser.
- **Schema `version` is a security input.** `MinabModule` caches the runtime by `schemaLoader(...).version`. If a host gives two different schemas (two tenants) the same `version`, the second tenant gets the first one's schema. This is how H2 was designed, and `docs/security.md` says it. Recommendation: in a later H card, make the service refuse a schema whose content changed under the same version (hash the tables once per loader call), or key the cache by a hash.

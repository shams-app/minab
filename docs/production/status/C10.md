# C10 Literals and kind tests compile to SQL that Postgres accepts

Status: done
Date: 2026-10-12
Branch / PR: claude/c10-literals-kind-tests

## Done
`check` no longer accepts the known programs that compile to SQL Postgres rejects. Literal-only parts of an expression run in Postgres. Kind tests follow D47. A user function that reads the record is not inlined into a query.

- **Typed literal parameters** (`src/language/minab-sql-compiler.ts`). When both sides of an operator are bare parameters (`$1 + $2`, `$1 < $2`), each one gets its Minab type: `$1::bigint`, `$1::numeric`, `$1::text`, and so on. The operand of a unary `-` that is a bare parameter gets its type too. A literal next to a column stays a bare parameter, as before, so no expected SQL in older tests changed, and the README `compile` block did not change either. `-5` is still one number. The `CITEXT` rules of D15 run after the typing, so a `TEXT` literal compared with a `CITEXT` value is still cast to `citext`.
  - This also fixes a wrong answer, not only a Postgres error: two literals compared as text before, so `10 < 9` was `true` in SQL.
  - A `let` value or another outer value bound as a parameter gets the same treatment (its type comes from the checker).
- **Kind tests (D47)** (`src/language/minab-type-checker.ts`, new code `type.kindTestNeedsJson`). `is` / `isnot` with `array`, `object`, `string`, `number` or `boolean` on an operand whose type is known and is not `JSON` is a check error. The message names the operand and its type: `"is number" tests the kind of a JSON value, but .total is DECIMAL`. `is null` and `isnot null` stay valid for every type. A `JSON` value that the caller holds (a `let` or a parameter) is bound as `jsonb`, as JSON text, so a JSON string reaches Postgres as `"dark"` and not as plain text.
- **Functions that read the record** (`src/language/minab-query-inlining.ts`). A function body that reads `.`, `^` or `#alias` is not inlined. The reason says why: `it reads ".", which inside a query would mean the query's row, not the record the function sees`. A `.` inside a `[...]` filter of the body is that filter's element, so it does not block. A `^` blocks unless it is inside two filters. The validator and the compiler both use `inlineBlocker`, so they use the same rule.
- **Tests:** `test/differential/cases/c10-literals.cases.ts` (29 cases, each with `expect`), `test/queries/cases/c10-literals.cases.ts` (12 cases on Postgres: `WHERE`, `SELECT`, `ORDERBY`, `LIMIT`, JSON locals, an inlined function), and `test/kind-tests.test.ts` (23 checker and SQL tests). The new code also has a case in `test/diagnostic-codes.test.ts`.
- **Docs:** spec §5.6 (D47 replaces "the grammar doesn't stop you from writing it", with D47's example) and §8.4 (which functions are inlined). `docs/reference/diagnostics.md` regenerated. `test/differential/README.md`: the rule "do not use only literals" is gone.

Differences from the card, noted here:
- **`INTEGER` literals are `bigint`, not `integer`.** The card says to use the type names of `CAST`, which maps `INTEGER` to `integer`. But columns are `bigint` (`src/host/ddl.ts`), and the interpreter allows any safe integer. With `integer`, `3000000000 + 1` would fail in Postgres. The other types use the `CAST` names.
- **Typing only where Postgres cannot infer the type.** The card allows this. Typing every literal would have changed the SQL in the root README, which this card may not edit.
- **`[1, 2] is array` is now a check error.** A list literal has an array type (`INTEGER[]`), not `JSON`, so D47's rule applies to it. A JSON object literal (`{ a: 1 }`) has type `JSON` and keeps the run-time test. The spec says this in §5.6.
- **`LIMIT` takes a number only** (grammar: `'LIMIT' limit=NUMBER`). The `LIMIT` query case has its literal parts in `WHERE` and `ORDERBY`.
- `test/spec-examples.test.ts`: the new §5.6 example block shows a wrong line with a ✗ note, so it is listed in `NOT_PROGRAMS`, the same as §3.4 and §7.7. Its error is tested in `test/kind-tests.test.ts`.
- **Merged with C9** (it landed on `main` first, as the card expected). C9 reads a JSON `null` as SQL `NULL` in a null test (`NULLIF(x, 'null'::jsonb)`). A `JSON` value from a `let` is now bound as `jsonb` there too, so a JSON string works in `x isnot null`. A query case covers it.
- When the operand's type cannot be known, the kind test keeps today's behavior (a run-time test). The operand's own failure is reported where it starts.

## Later
- `IN` with only literals (`1 IN [1, 2]`) still binds bare parameters, which Postgres may read as text. The card left `IN` to C9, which did not type them — C lane, a differential case first.
- `switch` with a literal subject and literal arms (`switch 1 { 1 => ... }`) binds bare parameters in `CASE $1 WHEN $2`. This is rare in a query — C lane, if a probe finds a wrong answer.
- `CAST(x AS INTEGER)` compiles to `integer`, but columns are `bigint`. A large value fails in Postgres and not in the interpreter — C lane (a differential case for large integer casts).

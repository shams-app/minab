# G1 — Embedding guide, API reference and docs index

| Lane | Kind | Size | Depends | Decisions | Release |

| G — Guides | Mechanical | M | [H3](H3.md), [H6](H6.md), [E5](E5.md) | [D09](../decisions.md#d09), [D38](../decisions.md#d38) | 0.3.0 |

## Goal

A developer can embed Minab in a new app using only the docs: an embedding guide (ports, where programs run, NestJS and browser walkthroughs that cite the example apps), a generated API reference, and one index page for all documentation. The root README points to them.

## Why now

0.3.0 is the "embeddable" release. The two example apps (H3, H6) and the Monaco integration (E5) exist, so the guide can cite real, tested code instead of inventing it.

## Read

- `docs/adr/0002-runtime-ports.md`
- READMEs of `src/runtime/`, `src/node/`, `src/nestjs/`, `src/browser/`, `src/monaco/`, `examples/nestjs/`, `examples/browser/`
- `docs/security.md` (Q3, if merged), `docs/performance.md` (Q4, if merged), `docs/compatibility.md` (Q5, if merged), `docs/reference/*`
- Root `README.md`
- Decisions D09 (TypeDoc), D38

## Ask first

None.

## Build

1. **`docs/guides/embedding.md`**:
   - what Minab gives a host and what the host gives Minab (schema, inputs, ports);
   - the API in 10 lines (`createMinab` → `prepare` → `run`);
   - the ports, one short section each, with the interfaces;
   - where programs run (D30) with the ADR's diagrams;
   - **NestJS walkthrough**, citing `examples/nestjs/` file by file (module setup, schema loader, program store, a transaction, the run endpoint);
   - **Browser walkthrough**, citing `examples/browser/` (worker, local rules, remote runs, routing, Monaco);
   - errors and codes (how to translate messages by code), limits, logs, security summary (link to `docs/security.md`), performance (link), compatibility (link), stored programs and `languageVersion`.
2. **API reference**: TypeDoc (D09) over the public entry points (`.`, `./node`, `./nestjs`, `./browser`, `./monaco`). `npm run docs:api` builds HTML into `out/api/` (not committed). A CI step (new workflow `docs-api.yml`) runs it with warnings treated as errors, so an undocumented public symbol fails. The website (W4) or the release (V2) publishes the output; write that in `docs/releasing.md` (one line; Q2's file).
3. **`docs/README.md`**: an index of every document: spec, showcase, guides, ADRs, reference (diagnostics, wire format), compatibility, security, performance, editors, releasing, the production plan.
4. **Root `README.md`**: a "Use Minab from your app" section (5–10 lines) linking the guide and the examples; update the status text (what runs, what is embeddable). Keep every output block that the examples test checks.
5. A link checker test (`test/docs-links.test.ts`): every relative link in `docs/**/*.md` and the root README points to a file that exists.

## Files

`docs/guides/embedding.md` (new), `docs/README.md` (new), `README.md`, `typedoc.json` (new), `package.json` (script, dev dependency), `.github/workflows/docs-api.yml` (new), `docs/releasing.md` (one line), `test/docs-links.test.ts` (new), TSDoc comments on public symbols that lack them.

## Do not touch

The Shamsine guide (G2). Code behavior.

## Output

Docs that let a new host integrate without reading the source.

## Test scenarios

- TypeDoc runs with no warnings.
- The link checker passes; break one link → it fails.
- Follow the NestJS walkthrough in a fresh folder (or confirm each cited file and line exists): write how you checked in your status file.

## Done when

The guide, the reference build, the index and the README section exist; the CI checks are green.

## Not here

Shamsine specifics (G2). The website's docs pages (W3 may link to these).

## Later

A hosted docs site (post-1.0, or part of the website later).

## If it grows

It should not.

# C1 — Differential test harness

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| C — Correctness | Mechanical | M | [B1](B1.md) | [D09](../decisions.md#d09) | 0.2.0 |

## Goal

One table-driven test runs the same Minab expression **in the interpreter** and **as SQL in Postgres**, and fails when the two answers differ. A second harness runs whole compiled queries on Postgres and checks their rows. Both run in every `npm test` with an in-process Postgres (PGlite), and against a real Postgres in CI.

## Why now

The recurring bug shape is "one runtime disagrees with the other" (ADR 0001 warns about it). C2–C5, L3–L6, X1 and X2 all prove their work with this harness. Each of them adds **its own case file**, so they never edit the same test file.

## Build

1. Add `@electric-sql/pglite` as a root dev dependency, same version as the playground.
2. **Move the DDL generator** `playground/src/engine/ddl.ts` to `src/host/ddl.ts` (it is pure and browser-safe). The playground imports it from there (leave `playground/src/engine/ddl.ts` as a one-line re-export so playground imports keep working). Keep `playground/test/ddl.test.ts` green.
3. **`test/support/database.ts`**: `openTestDatabase()` returns a small API (`exec`, `query`, an executor for Minab) backed by **PGlite in-process**, or by real Postgres when `MINAB_TEST_DATABASE_URL` is set (same API). It loads `citext`. One database per test file; each case runs in its own transaction or schema so cases do not see each other's rows.
4. **Scalar harness** `test/differential/`:
   - `harness.ts`: for each case, (a) interpret the expression with the given record, (b) compile it as `FROM One SELECT <expr> AS v` against a one-row table `One` (or `FROM <table> WHERE <key> == <id> SELECT <expr> AS v` when the case has a record), run it on the database, (c) compare. Comparison is type-aware: `DECIMAL` by exact value, dates as ISO text, `null` equal to `null`, and "both raised an error" counts as agreement when both errors map to the same meaning (for example division by zero).
   - `differential.test.ts` loads every `cases/*.cases.ts` with `import.meta.glob('./cases/*.cases.ts', { eager: true })` (Vitest supports it). **Adding a case file needs no change to any shared file.**
   - Case shape: `{ name, expr, schema?, record?, expect?, knownGap?: { card: 'C3', note } }`. When `expect` is given, both answers must equal it. When `knownGap` is given, the test asserts the two answers **differ** (so the case documents a known bug); the card that fixes it removes `knownGap`, and the test then requires agreement. A `knownGap` case that suddenly agrees fails with "gap fixed? remove knownGap".
   - `README.md`: how to add a case; the rule "one file per phase: `cases/<ID>-<topic>.cases.ts`".
5. **Query harness** `test/queries/`: the same idea for whole programs: `cases/*.cases.ts` with `{ name, schema, rows, program, expectRows, ordered? }`. It compiles the program, runs it on the database and compares the rows. Also asserts that `check` is clean for the program.
6. **First cases** (one file per topic, prefixed `c1-`):
   - arithmetic on `INTEGER` and `DECIMAL`, comparisons, `AND`/`OR`/`NOT`, `IN`, `LIKE` with `%` and `_`, `null` rules (§7.7);
   - known gaps, each marked with the card that fixes it: `0.1 + 0.2 == 0.3` (C2), `CAST(3.7 AS INTEGER)`, `CAST("12" AS INTEGER) + 1`, `CAST(5 AS TEXT) == "5"` (C3), `7 / 2` on two integer columns and `5 % 0` (C4), `CITEXT` compared with text (C5; this may be a check error today: then record it as a known gap in the query harness or as a note in `C5`'s card's tests);
   - query cases for today's working shapes: filter, project, order, group by a relation, aggregate over a relation, `EXISTS`, `LEFTJOIN`.
7. CI: nothing to add. `npm test` runs it with PGlite; Q1's Postgres workflow runs it against Postgres 16 through `MINAB_TEST_DATABASE_URL`.

## Do not touch

The interpreter and compiler (fixes belong to C2–C8). Expected results of existing tests.

## Output

Two harnesses with one-file-per-phase case files. Every later "both runtimes" claim is proven here.

## Test scenarios

- A case with a wrong `expect` fails, showing both answers.
- A `knownGap` case that agrees fails with the "gap fixed?" message.
- The suite passes with PGlite locally and with `MINAB_TEST_DATABASE_URL` set (if you have a Postgres).
- PGlite starts once per test file (time the suite; it should add only a few seconds).

## Done when

Both harnesses run in `npm test`, the first case files pass (known gaps marked with their cards), the playground still passes after the DDL move.

## Not here

Fixing any gap (C2–C7). Fuzz tests (Q3).

## Later

None expected.

## If it grows

The query harness's first cases may be fewer (keep filter, group by a relation, `EXISTS`). Both harnesses must exist.

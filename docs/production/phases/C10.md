# C10 — Literals and kind tests compile to SQL that Postgres accepts

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| C — Correctness | Mechanical | M | [C2](C2.md), [X1](X1.md), [X2](X2.md) | [D47](../decisions.md#d47) | 0.4.0 |

## Goal

`check` no longer accepts the known programs that compile to SQL Postgres rejects. Literal-only parts of an expression (`1 + 2`, `.price * (1 + 0.2)`) run in Postgres. The kind tests (`is array`, `is number`, …) are checked as D47 says. A user function that reads `.`, `^` or `#alias` is not inlined into a query, so its meaning cannot change without a word.

## Why now

Point 1 of "What production level means" says `check` never accepts a program that compiles to SQL the database rejects. A probe with the differential harness on `main` (2026-10-11) found these. Each one checks clean today:

| Expression | Interpreter | Postgres |
|---|---|---|
| `1 + 2`, `-1 + 2`, `1 + 2.5`, `7 % 2` | the answer | error "operator is not unique: unknown + unknown" |
| `.a * (1 + 2)`, `.a > 1 + 2`, `.x * (1 + 0.2)` | the answer | the same error |
| `.a is array`, `.a is number`, `.x is number`, `.s is string`, `.yes is boolean`, `TODAY() is string` | an answer from the JavaScript value (`.a is number` is `true`, `.x is number` is `false`) | error "function jsonb_typeof(bigint) does not exist" (or `numeric`, `text`, `date`, …) |
| `"a" is string` | `true` | error "invalid input syntax for type json" |

Literal-only parts are common in real queries, for example `WHERE .total > 50 + 50` or `SELECT .price * (1 + 0.2) AS gross`. The Later lists of C1, C2, C4, X1 and X2 name these gaps.

## Ask first

None. D47 decides the kind tests. The other two steps follow from point 1 of "What production level means".

## Build

1. **Typed literal parameters.** Postgres cannot choose an operator for two parameters with no type (`$1 + $2`). Bind each literal with its type, as the checker infers it. Use the same SQL type names as `CAST` does (the compiler's type map), for example `$1::numeric` for a `DECIMAL` literal and `$1::text` for a `TEXT` literal. Typing every literal is the simplest rule; typing only where Postgres cannot infer the type is also fine. Keep `-5` as one number (the rule in `unary()`). Keep the `CITEXT` rules of D15: a `TEXT` literal compared with a `CITEXT` column. Update the SQL text expected by existing tests only for the added casts, and check that each one still means the same thing.
2. **Kind tests (D47).**
   - `is` or `isnot` with `array`, `object`, `string`, `number` or `boolean` on an operand whose type is known and is not `JSON` is a check error with a new code (for example `type.kindTestNeedsJson`), with the message D47 shows. It names the operand's type.
   - `is null` and `isnot null` stay valid for every type.
   - A `JSON` operand keeps the run-time test in both runtimes. When the `JSON` operand is a literal or a parameter, bind it as `jsonb`.
   - If the type of an operand cannot be known, keep today's behavior and say so in your status file.
3. **Functions that read the record.** A user function whose body reads `.`, `^` or `#alias` is not inlined into a query. `check` reports `query.functionNotInlinable`, with a reason that says why. Today the body is copied as it is, so `.` silently becomes the query's row (X2 Later). Use the same rule in the validator and in the compiler.
4. **Cases and tests.**
   - `test/differential/cases/c10-literals.cases.ts`, with `expect` on every case.
   - `test/queries/cases/c10-literals.cases.ts`, for literal-only parts inside real queries (`WHERE`, `SELECT`, `ORDERBY`, `LIMIT`).
   - Checker tests for the new code and for the function rule (in `test/typechecking.test.ts` or a new test file).
5. **Docs.** Spec §5.6: D47 replaces "the grammar doesn't stop you from writing it". Spec §8: which functions are inlined into a query. Regenerate `docs/reference/diagnostics.md` (`npm run docs:diagnostics`).

## Output

Literal-only expressions run in Postgres. Kind tests are checked. A function that is inlined into a query keeps its meaning.

## Test scenarios

- `1 + 2` is `3`, `-1 + 2` is `1`, `1 + 2.5` is `3.5`, `7 % 2` is `1` and `7 \ 2` is `3`, in both runtimes.
- With `ITEM_SCHEMA` and `.a` = 4: `.a * (1 + 2)` is `12`, `.a > 1 + 2` is `true`, and `.x * (1 + 0.2)` gives the exact decimal, in both runtimes.
- The query `FROM Item WHERE .a > 1 + 2 SELECT .id` runs on PGlite.
- `"a" + "b"`, `"a" == "a"`, `1 < 2`, `ABS(-3)` and `ROUND(2.5)` still agree (they agree today).
- With `ITEM_SCHEMA`: `.x is number`, `.a is array`, `.s is string` and `TODAY() is string` are check errors with the new code. `.n isnot null` gives no error.
- `config is object` on a `JSON` local, and `.j is array` on the `JSON` column of the X1 cases, give the same answer in both runtimes. The X1 cases still pass.
- A function that reads `.`, called in a `SELECT`, gives `query.functionNotInlinable`. A function that reads only its parameters is still inlined. The X2 cases still pass.

## Done when

- Every scenario above passes.
- The X1 and X2 cases and the golden corpus test are green. (The corpus uses `is object` only on `JSON` values.)
- The spec and the diagnostics reference are updated.
- `changes/C10.md`: type `fixed`, scope `language`, `breaking: true` (some programs that checked before are now check errors).

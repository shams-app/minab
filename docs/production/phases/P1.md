# P1 — Group expressions: aggregates over the rows of a group

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| P — Shamsine pivot | Design → Mechanical | M | [R5](R5.md), [X2](X2.md), [C9](C9.md), [E5](E5.md) | — | `next` channel, then the next release |

## Goal

A host can ask for a **group expression**: one expression that is evaluated for a group of rows of one table, like the `SELECT` part of a `GROUPBY` query, but without the query around it. `SUM(.Revenue) - SUM(.Cost)` is the profit of the group. `SUM(.Price * .Units)` multiplies per row and then adds. `SUM(.Profit) / SUM(.Revenue)` is a ratio of two sums. It checks, it gets editor help, and it runs in the interpreter over rows the host gives.

This card is the language half. P2 turns the same expression into SQL.

## Why now

Shamsine's pivot table (monorepo plan `docs/pivot/`, card PX.4) lets users add a "calculated value". Every cell, every subtotal and the grand total must compute the expression **on its own rows**, never on a column of results (that is Excel's known wrong grand total). A group of rows is exactly what `GROUPBY` already gives (spec §4.2, item 4: `.` is a row within the group, `SUM(.total)` works). What is missing is a program that is only the expression, with a way to say "the group is rows of table T".

## Ask first

All in one message, with these recommendations:

1. **Division by zero.** In a pivot, a cell with no revenue must give an empty cell, not stop the whole table. Today `/`, `%` and `\` by zero are the error `eval.divisionByZero` in both runtimes (spec §7.3). Proposed: **in a group expression, division by zero gives `null`** in both runtimes (SQL: `x / NULLIF(y, 0)`). Every other program keeps the error. A host that wants to know that it happened can check `y` with its own `SUM`.
2. **What a group expression may contain.** Proposed: any plain expression (literals, arithmetic, comparison, `if` and `switch`, the number, text and null built-ins) whose only data is the rows of the group, read as `.Column`. Refused with one code, `groupExpression.unsupported` (the construct named in `params`): statements, `FROM` queries, user functions, host functions, `$`, relation traversal (`.customer.name`, `.orders`), and inputs. `currentUser` and `NOW()` stay allowed only if the host declared them (they are host inputs and clock, not data).
3. **Spelling of columns.** Proposed: as in a `GROUPBY` query, `.Revenue`, and quoted names (L3) for names with spaces or Persian letters. Host editors may show names without the dot as a convenience, but the stored program text is always the Minab text.

## Build

1. **Rule context.** `MinabRuleContext` gets `groupTable?: string` (a table of the schema). It cannot be combined with `recordTable` or `isFieldRule` (a clear error). Add `ProgramKind` member `'group-expression'`; `classifyProgram` returns it when `groupTable` is set and the program is an expression.
2. **Checker.** Inside a group expression, `.` is a row **in the group** (the `GROUPBY` rule). An aggregate (`SUM`, `AVG`, `MIN`, `MAX`, `COUNT`) takes an expression over `.` columns: `SUM(.Price * .Units)` is allowed and typed as `SUM` of the product. A `.Column` outside an aggregate is the error **`aggregate.fieldOutsideAggregate`** with `params.name`; the message says "wrap `Price` in SUM, AVG, MIN, MAX or COUNT". An aggregate inside an aggregate is `aggregate.nested`. Numbers only for `SUM`/`AVG`; `MIN`/`MAX`/`COUNT` follow the existing signatures. A construct that Ask first #2 refuses is `groupExpression.unsupported`. Add every new code to the registry (B1 rules: stable code, English text, `params`).
3. **Division by zero** as answered in Ask first #1, in the checker's result type (the result of `/` is nullable) and in the interpreter.
4. **Interpreter.** `run` of a group expression takes `RunInputs.groupRows: Row[]` (the rows of one group, plain values by column name). An empty list is a valid group: `SUM` and `AVG`, `MIN`, `MAX` give `null`, `COUNT` gives `0` (as `GROUPBY` does today). Result is the value, with the exact `DECIMAL` rules of C2. `analysis.tier` is `local` (no data port is used).
5. **Analysis.** `ProgramAnalysis` gets `groupColumns: string[]` (the columns of `groupTable` the program reads, in first-use order) and `aggregates: Array<{ fn: string; columns: string[] }>`. A host uses them to plan its query and to say "at most 5 calculated values" or "only SUM and AVG".
6. **Editor.** After `.`, completion offers the columns of `groupTable` (numbers first when inside an aggregate); hover says "column of the group". `ExpressionEditor`-style hosts pass `ruleContext: { isFieldRule: false, groupTable }` (R5/E5 plumbing; no new API if it already passes the context through). Update `docs/guides/shamsine.md` with one section "Calculated values for a pivot" and an example.
7. **Spec.** Add a short section to the spec (§4.2.1 "Group expressions") that states items 1–5. This is a spec change: follow `.cursor/rules/spec-governance.mdc` (the approved Ask first answers are the proposal).

## Do not touch

The SQL compiler (P2). The wire format. Existing `GROUPBY` query behaviour (a query keeps the error on division by zero).

## Output

`prepare(source, { ruleContext: { isFieldRule: false, groupTable } })` gives a prepared group expression with `diagnostics`, `resultType`, `analysis.groupColumns` and `analysis.aggregates`; `run({ groupRows })` gives its value. Codes: `aggregate.fieldOutsideAggregate`, `aggregate.nested`, `groupExpression.unsupported`.

## Test scenarios

- `SUM(.Revenue) - SUM(.Cost)` over rows `(20,5)`, `(20,8)`, `(8,10)` is `25`; over the first two rows `27`.
- `SUM(.Price * .Units)` over `(10,2)`, `(5,4)`, `(8,1)` is `48` (not `23 * 7`).
- `SUM(.Profit) / SUM(.Revenue)` with all revenue `0` gives `null`, not an error; with no rows gives `null`.
- `.Price * 2` alone: `aggregate.fieldOutsideAggregate`, `params.name = "Price"`, range on `.Price`.
- `SUM(SUM(.Price))`: `aggregate.nested`. `FROM Order SELECT …`, `.customer.name`, a user function call: `groupExpression.unsupported`.
- `DECIMAL` money: `SUM(.Price)` over `0.1`, `0.2` is exactly `0.3`.
- A quoted name (`.\`Total cost\``, a Persian name) works.
- Completion after `.` lists the group table's columns; `analysis.groupColumns` is `["Revenue","Cost"]` for the first example.
- Fuzz: random group expressions over random rows never throw; every run is a value, `null` or a coded error.

## Done when

All scenarios have tests. `npm test`, lint and format pass. The spec section, the Shamsine guide section and the codes list are updated. The playground still builds (`cd playground && npm test && npm run build`).

## Not here

SQL (P2). Calculated values that name other calculated values: the host expands those names before it calls `prepare`. A new built-in. Group expressions in a `GROUPBY` query (they already work there).

## Later

# C8 — Checker completeness

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| C — Correctness | Mixed | S | [L1](L1.md) | [D18](../decisions.md#d18) | 0.2.0 |

## Goal

Every node type that can fail type inference reports its own failure, even when it is nested inside another expression. `ORDERBY` on a non-alias expression is defined in the spec and pinned by a test.

## Why now

`ParentRecord`, plain `NameRef` and `Subquery` have failure paths in the checker but are not registered in the validator, so a nested failure can go unreported, and `check` passes a program that then fails. It waits for L1 because L1 made every function call a `NameRef` callee, which must stay excluded.

## Read

- `src/language/minab-validator.ts` (the registered node types and why: header comment)
- `src/language/minab-type-checker.ts`: `inferTypeDispatch`, `inferNameRef`, `inferSubquery`, the `ParentRecord` path
- `docs/roadmap.md` Phase 7 (why registering every `Expression` was reverted)
- Spec §4.1
- Decision D18

## Ask first

None.

## Build

1. Register exactly `ParentRecord`, `NameRef` (but **not** a `NameRef` in a call's callee position) and `Subquery`. Do not register all of `Expression`.
2. Make sure each failure is reported once (the `origin` mechanism from Phase 7), not twice (by the node and by its parent).
3. For each of the three: a test where it fails **nested** under a registered parent (for example `COUNT(.orders[^.missing == 1])`, an unknown `NameRef` inside an `IN` list, a broken subquery inside a comparison) and the diagnostic points at the inner node.
4. **`ORDERBY`** per D18 (option a): spec §4.1 says `ORDERBY` takes any expression over the source row, or a `SELECT` alias; add a test that pins both forms (SQL text and a query-harness run). If D18 is option b: the checker rejects non-alias expressions with a new code.

## Files

`src/language/minab-validator.ts`, `src/language/minab-type-checker.ts` (only if a failure path needs an `origin`), `src/language/diagnostics/codes.ts` (if a code is new), tests (`test/typechecking.test.ts` or `test/nested-failures.test.ts` new), query cases `test/queries/cases/c8-orderby.cases.ts`, spec §4.1.

## Do not touch

Other checks.

## Output

No silent nested failures.

## Test scenarios

Listed in Build 3 and 4. Also: a valid program with the three node types nested deep gets no new diagnostic (no false positives), and a function call `f(1)` gets no diagnostic on `f`.

## Done when

The tests pass; every showcase example still checks as before (and L2's spec-examples test, if it is merged); spec §4.1 updated.

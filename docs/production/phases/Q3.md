# Q3 — Security hardening

## Goal

Prove that a program written by an end user cannot hurt its host: it cannot crash it, hang it, inject SQL, read outside its schema, or leak personal data into logs. Write down what a host must do to stay safe, and how to report a security problem.

## Why now

From 0.3.0, Shamsine runs user-written programs on its server. This must hold before that release (D02).

- `src/language/minab-sql-compiler.ts`: `quoteIdent` and how values become parameters
- `src/language/minab-interpreter.ts`: `like()`

## Build

1. **Fuzz tests** in a new `test/fuzz/` folder (with a README), using `fast-check` (D09) with a fixed seed (print the seed when a test fails; `MINAB_FUZZ_RUNS` raises the count locally):
   - **prepare never throws**: random token sequences and mutated programs (take spec and showcase programs, then delete, swap or repeat tokens). `prepare` must return diagnostics, never throw, and finish each input in under 200 ms;
   - **run stays inside its limits**: random well-typed expressions from a small generator, run against PGlite with tight limits. Every run ends with a value or a coded error (`limit.*`, `eval.*`), never an uncaught exception, and never runs past the wall-time limit plus 50 ms.
   - CI runs 2,000 cases per property.
2. **Prepare-time limits**: add `limits.maxSourceLength` and `limits.maxNesting` (D36) to `src/runtime/limits.ts` if R4 did not; test a 5,000-level nested expression and a 1 MB source: both give a coded diagnostic, no stack overflow.
3. **SQL injection tests** (`test/security/sql-injection.test.ts`): table, column and `sqlName` values containing `"`, `'`, `;`, `--`, backticks and Unicode; string literals with quotes and backslashes. Run on PGlite: the queries work, nothing else runs, and **no value ever appears in the SQL text** (only `$n` placeholders).
4. **`LIKE` cannot be slow**: patterns like `%a%a%a%a%a%a%b` against a 10,000-character text finish in under 50 ms in the interpreter. If the current regex-based `like()` fails this, replace it with a linear-time matcher (keep the differential tests green).
5. **The schema is the read surface**: a test that `#Secret` (not in the schema) is a scope error, and that the NestJS module (H2) prepares with the schema its `schemaLoader` returns for the request, never one sent by the client.
6. **Run endpoint**: tests that H2's controller refuses source text unless development mode is on (D34), refuses a batch over the limit, and never returns SQL text or stack traces in error bodies.
7. **Logs**: tests that the Nest logger adapter escapes newlines, respects the cap and is off by default when `NODE_ENV=production` (D37).
8. **`SECURITY.md`** (root): supported versions, how to report (D43), what to expect (first answer within 7 days).
9. **`docs/security.md`**: the threat model for hosts. Who writes programs (D01). What a program can do (read the schema it is given; call the host functions it is given; nothing else). What the host must do: scope the schema per tenant or user; keep limits on; never accept SQL or a schema from a browser; run stored programs by id (D34); keep logs off in production; consider database row-level security; use a read-only database role for programs that do not write.
10. **CodeQL**: `.github/workflows/codeql.yml` for JavaScript/TypeScript, if the repository is public (D04); otherwise write it under Later.

## Files

`test/fuzz/*` (new), `test/security/*` (new), `src/runtime/limits.ts`, possibly `src/language/minab-interpreter.ts` (`like`), `SECURITY.md` (new), `docs/security.md` (new), `.github/workflows/codeql.yml` (new), `package.json` (`fast-check`).

## Do not touch

The NestJS module's API (report problems to the owner instead of redesigning it), the spec.

## Output

Fuzz and security suites in CI; a security policy; a threat model hosts can follow.

## Test scenarios

Listed in Build 1–7. Every bug found gets a regression test that fails without the fix.

## Done when

- The fuzz and security suites are green in CI.
- `SECURITY.md` and `docs/security.md` exist.
- Every problem found is fixed, or (if it belongs to another lane's code and is large) reported to the owner with a recommendation.

## Not here

Performance budgets (Q4). Row-level security setup in a real app (the host's job; document only).

## Later

Third-party security review before 1.0, if the owner wants one (note it for V4).

## If it grows

CodeQL may move to Later. The fuzz generator for runs may start small (arithmetic, comparisons, `IN`, `LIKE`, aggregates over one relation); widening it can move to Later. The injection, limits and `LIKE` items must stay.

# C9 — Null and `IN`: one answer in both runtimes

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| C — Correctness | Mechanical | M | [C4](C4.md), [L4](L4.md), [X1](X1.md) | [D46](../decisions.md#d46) | 0.4.0 |

## Goal

When a value is `null` at run time, the interpreter and Postgres give the same answer. Arithmetic gives `null`, and ordering and `LIKE` give `false` (D46). `IN` never gives `null` in SQL, as spec §7.7 says. `IN` with a subquery runs in the interpreter. A JSON `null` counts as `null` in SQL too. No `knownGap` case is left.

## Why now

V4 (the 1.0 gate) needs no `knownGap` case and no known wrong answer. Three cases in `c1-known-gaps.cases.ts` still say `card: 'none yet'`. A probe with the differential harness on `main` (2026-10-11) found more cases of the same kind. In each one, `check` accepts the program, and the two runtimes give different answers:

| Expression (`.n`, `.m`, `.t` are `null`, `.a` is 4, `.b` is 0) | Interpreter | Postgres |
|---|---|---|
| `.n + .a`, `.n - .m`, `-.n`, `.n * 2`, `.n / 2`, `.n / .b`, `.n % 2`, `.n \ 2` | error "expected a number" | `null` |
| `.n < 5`, `.n > .a`, `.t LIKE "a%"` | error "not a valid operator against null" | `null` |
| `.n IN [1, 2]`, `.a IN [1, null]` | `false` | `null` |
| `.n IN [1, null]` | `true` | `null` |
| `NOT (.n IN [1, 2])`, `NOT (.a IN [1, null])` | `true` | `null` |
| `.a IN (FROM Item SELECT .a)` (and every other subquery) | error "IN needs a collection on the right" | `true` or `false` |
| `CAST("null" AS JSON) is null` | `true` | `false` |

## Build

1. **Arithmetic with a `null` operand (D46).** In the interpreter, `+`, `-`, `*`, `/`, `\`, `%` and unary `-` give `null` when an operand is `null`. This comes before any other check, so `null / 0` is `null`. Postgres already answers `null`: keep it so (check `divisionSql` and `wholeDivisionSql`). The checker types the result as nullable when an operand is nullable. Check this, and fix it only if it is wrong.
2. **Ordering and `LIKE` with a `null` operand (D46)** give `false` in both runtimes.
   - Interpreter: return `false` instead of failing.
   - Compiler: wrap `<`, `<=`, `>`, `>=` and `LIKE` in `COALESCE(…, false)` when an operand can be `null`. You may keep the plain form where `null` and `false` keep the same rows, so Postgres can still use an index: in a `WHERE`, `HAVING` or filter condition, when the comparison is reached only through `AND` and `OR` (not under `NOT`, `==`, `!=`, `if`, `switch` or a function). Prove both forms with cases.
   - The literal `null` next to these operators stays a check error (§7.7 rule 3). Keep its test.
3. **`IN` is repeated `==` (spec §7.7).** SQL `IN` is three-valued, and Minab `IN` is not. Compile `IN` so it never gives `null`, for a list literal and for a subquery. Keep the `CITEXT` casts of D15. For example, compile a list as `(v IS NOT DISTINCT FROM a OR v IS NOT DISTINCT FROM b)`, and a subquery as `EXISTS (SELECT 1 FROM (<subquery>) AS s WHERE s.<column> IS NOT DISTINCT FROM v)`. When `v` is not a plain column or parameter, compute it once, or show that repeating it is safe. `NOT (x IN …)` is then right by itself.
4. **`IN` with a subquery in the interpreter.** A one-column subquery on the right of `IN` gives the list of its values, with the same `==` rules as a list. Today a rule such as `.customer_id IN (FROM Customer WHERE .vip SELECT .id)` fails in the interpreter.
5. **A JSON `null` is `null`.** Spec §5.6 says `x is null` and `x == null` mean the same for every expression. For a `JSON` operand, compile `is null`, `isnot null`, `== null` and `!= null` so that a JSON `null` counts as `null`, for example `(x IS NULL OR jsonb_typeof(x) = 'null')`.
6. **Sweep the other places where a `null` meets an operator.** Add one differential or query case for each one that both runtimes can run: `ORDERBY` on a nullable column (where the nulls go), `MIN`, `MAX`, `SUM` and `AVG` over only nulls, `switch` and `if` on a `null`, and a `COALESCE` chain. Fix a disagreement when the fix is small. Otherwise write it under Later, with the exact case.
7. **Cases.**
   - Remove the three cases from `test/differential/cases/c1-known-gaps.cases.ts`. Delete the file when it is empty.
   - Add `test/differential/cases/c9-null-rules.cases.ts`, with `expect` on every case.
   - Add `test/queries/cases/c9-in.cases.ts` for `IN` with a subquery, `NOT IN`, and a `WHERE` on a nullable column.
8. **Spec and showcase.**
   - §7.7: a short part "a `null` value at run time", with D46's rules and its example.
   - §5.1: the `null` row of the operator table.
   - §5.6: a JSON `null` is `null`.
   - Showcase: one example (`COALESCE` before arithmetic).

## Output

## Test scenarios

Use `ITEM_SCHEMA` and the record `{ id: 1, n: null, m: null, t: null, a: 4, b: 0 }`. Each case runs in both runtimes, with `expect`:

- `.n + .a`, `.n - .m`, `-.n`, `.n * 2`, `.n / 2`, `.n / .b`, `.n % 2` and `.n \ 2` are `null`.
- `.n < 5`, `.n >= 5`, `.n > .a` and `.t LIKE "a%"` are `false`. `NOT (.n < 5)` is `true`.
- `.n IN [1, 2]` is `false`. `.n IN [1, null]` is `true`. `.a IN [1, null]` is `false`. `.a IN [4, null]` is `true`. `NOT (.n IN [1, 2])` and `NOT (.a IN [1, null])` are `true`.
- `.a IN (FROM Item SELECT .a)` is `true`. `.a IN (FROM Item SELECT .b)` is `false`. `.n IN (FROM Item SELECT .m)` is `true` (both are `null`).
- `CAST("null" AS JSON) is null` is `true`.
- The query `FROM Item WHERE .n < 5 SELECT .id` returns no row with a `null` `n`, and `FROM Item WHERE NOT (.n < 5) SELECT .id` returns it.
- `.n < null` is still a check error.

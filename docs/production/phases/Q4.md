# Q4 — Performance budgets

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| Q — CI, release and quality | Mechanical | M | [R4](R4.md), [H5](H5.md) | [D02](../decisions.md#d02) | 0.3.0 |

## Goal

Measure the speeds that matter for Shamsine and the website, agree on budgets, and make CI fail when a change breaks one.

## Why now

The runtime (R4) and the browser path (H5) exist, so the real numbers can be measured. Shamsine's M.16 asks for "typing in a field stays under one frame".

## Read

- `src/runtime/` (README and `minab.ts`: the service cache)
- `src/browser/` (README; the bundle numbers H5 recorded in `bench/bundle.json`)
- `docs/production/status/R2.md`, `R4.md`, `H5.md`
- Old roadmap Phase 6 notes on parser modes (`.cursor/rules/language-implementation.mdc`, "Parser mode")

## Ask first

Confirm the budget table below, or give other numbers. (Recommended: these, measured on CI's `ubuntu-latest`, with a 1.5× allowance for noisy machines.)

| What | Budget |
|---|---|
| `prepare` a typical one-line rule, warm service cache (Node) | ≤ 5 ms median |
| First `prepare` with a new schema (cold, production parser mode) | ≤ 150 ms |
| `run` a prepared rule that needs no data (Node) | ≤ 0.05 ms median |
| Re-run 100 prepared local rules after one field changes (browser worker, measured in Node with the worker code) | ≤ 8 ms total |
| `run` a correlated rule with one data call (PGlite in-process), excluding database time | ≤ 2 ms |
| Browser worker bundle, gzip | H5's measured size + 10% |
| Language server completion on a 200-line file | ≤ 50 ms |
| Memory with 50 cached schemas | ≤ 200 MB resident |

## Build

1. `bench/` folder (with a README): one script per row, using `performance.now()` loops with warm-up (no new dependency). `npm run bench` prints a table and writes `bench/results.json`.
2. `bench/budgets.json` holds the agreed numbers. `npm run bench:check` compares results with budgets × 1.5 and fails above them.
3. New workflow `perf.yml`: runs `bench:check` on pull requests that change `src/**`; the result table goes to `$GITHUB_STEP_SUMMARY`.
4. If a budget fails today, fix the biggest cause inside the runtime (for example: share Langium's shared services across schemas; cache prepared programs by source hash and schema version; avoid re-validating unchanged documents). Each fix needs a test that its behavior is unchanged.
5. `docs/performance.md`: the numbers, what each one means for a host, how to profile (Node `--cpu-prof`, Chrome performance panel for the worker), and the settings that matter (cache size, parser mode).

## Files

`bench/*` (new), `.github/workflows/perf.yml` (new), `package.json` (scripts), `docs/performance.md` (new); runtime files only if a fix is needed.

## Do not touch

The public runtime API (a fix must keep it).

## Output

Budgets in CI; a performance page for hosts.

## Test scenarios

- `bench:check` fails when a budget is lowered below the measured number (try once, restore).
- Any performance fix keeps the full test suite green and has a test for the cache behavior it adds.

## Done when

Budgets are agreed, enforced in CI, and met (or a fix landed); `docs/performance.md` exists.

## Not here

Set-based batch runs (post-1.0). Website Lighthouse scores (W4).

## Later

Benchmarks against a real Postgres over the network (only useful once a host runs them).

## If it grows

The memory and language-server rows may move to Later if they need tools that are not ready (write down why). The prepare and run rows must stay.

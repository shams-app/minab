# C7 — `GROUPBY` on a related field

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| C — Correctness | Mechanical | S | [C1](C1.md) | — | 0.2.0 |

## Goal

`FROM Order GROUPBY .customer.country SELECT KEY AS country, SUM(.total) AS revenue` compiles to SQL that Postgres accepts and gives the right rows.

## Why now

It passes `check` but the SQL fails in Postgres ("subquery uses ungrouped column"). A query that checks must run. C1's query harness can now prove it on a real database.

## Read

- `src/language/minab-sql-compiler.ts`: the `GROUPBY` part of `query()`, `selectClause()`, `fieldOrOuter()`, `refSubquery()`
- `test/sql-compilation.test.ts` (expected SQL for grouping), `test/queries/README.md` (C1)
- The 2026-09-19 entry in `docs/status.md` about this bug

## Ask first

None.

## Build

1. Compile a `GROUPBY` key that walks a relation so that `GROUP BY` and `SELECT` agree. Two known ways: (a) join the related table once (`LEFT JOIN "Customer" AS "_g0" ON "_g0"."id" = "Order"."customer_id"`) and group by and select `"_g0"."country"`; (b) group by the foreign key and project through it. Pick (a) unless it breaks other shapes; it also works for several hops (`.customer.region.name`) and gives one join per path.
2. `KEY` and `KEY.field` in `SELECT`, `HAVING` and `ORDERBY` use the same expression.
3. Update the expected SQL in `test/sql-compilation.test.ts` on purpose (the diff is supposed to change).
4. Query cases `test/queries/cases/c7-groupby.cases.ts`: one hop, two hops, a nullable relation (orders with no customer form one `null` group), with `HAVING` and `ORDERBY` on the key.

## Files

`src/language/minab-sql-compiler.ts`, `test/sql-compilation.test.ts`, query cases.

## Do not touch

Multi-key `KEY` (X2). Grouping by the relation itself (`GROUPBY .customer`, which already works; keep it working).

## Output

Grouping by any related field works.

## Test scenarios

Listed in Build 4. Also: `GROUPBY .customer` with `KEY.name` gives the same SQL as before (or an equivalent one that the query harness proves).

## Done when

The query cases pass on PGlite and on Postgres in CI.

## Not here

Several keys (X2).

## Later

None expected.

## If it grows

It should not.

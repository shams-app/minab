# R1 — ADR 0002: runtime ports and where programs run

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| R — Runtime | Design | M | [A2](A2.md) | [D01](../decisions.md#d01), [D27](../decisions.md#d27)–[D38](../decisions.md#d38) | 0.3.0 |

## Goal

A written, signed-off architecture (ADR 0002) for one Minab runtime that runs in the browser, in Node/NestJS and in the CLI: the API hosts call, the ports Minab calls out through (with TypeScript interfaces), how runs travel between browser and server, and how Shamsine uses it. No production code.

## Why now

Every R, H and E phase builds against this document. It needs the runtime decisions (A2), and it can be written while B1 runs.

## Build

1. `docs/adr/0002-runtime-ports.md` with these sections:
   1. **Context**: today's two hand-written hosts; what Shamsine needs (from the M cards).
   2. **Decision summary**: one line per decision (D27–D38) with its answer.
   3. **Driving API** (TypeScript): `createMinab(options)` → `Minab`; `minab.prepare(source, { ruleContext, expect, languageVersion })` → `PreparedProgram` with `diagnostics`, `kind`, `resultType`, `analysis`, `compile()`, `run(inputs, ports, { signal, limits })`; `minab.dispose()`. Inputs (record, `$`, host input values) are given; ports are asked.
   4. **Driven ports** (TypeScript interfaces): `DataPort` (`execute(query, { signal })`), `WritePort` (transaction and execute; interface now, built in X5), host functions (declarations at `createMinab`, `call(name, args, { signal })`), host inputs (declarations), `ClockPort` (`now()`, `timeZone`), `EventSink` (one stream: statement, log, timing — D33), `ProgramStore` (for runs by id — D34), schema (`MinabSchema` with `version` — D29).
   5. **Results and errors**: the run result (`value`, `logs`, `stats`) and the error shape (`code`, `message`, `range`, `params`); code areas (`eval.*`, `limit.*`, `data.*`, `compile.*`, `cancelled`), building on B1's registry; how hosts map codes to HTTP statuses.
   6. **Limits and cancellation** (D36): where each limit is checked; `AbortSignal` passed to every port call.
   7. **Analysis**: what `analysis` contains (tables and record fields read, inputs and host functions used, `needsData`, tier `local`/`data`, writes) and the rule that it is conservative (when unsure: `data`).
   8. **Topologies**, each with a Mermaid sequence diagram: CLI; NestJS server (stored program, request transaction); browser local (worker, tier `local`); browser delegated (program id + inputs to the server, D28/D34); playground (PGlite inside the worker).
   9. **Wire format v1** outline (R6 implements it): request and response JSON shapes, batches, value encoding (`DECIMAL` as string — D17, dates as ISO strings — D21, `UUID` as string, `JSON` as is), version field.
   10. **Concurrency**: one Langium service set per schema version (cached, size-capped); one document per `prepare`, released after building; how concurrent runs stay independent (the spike's result, Build 2).
   11. **Packaging** (D31, D32): the entry points list, ES modules plus a CommonJS bundle, optional peers, `typesVersions` for older TypeScript resolution.
   12. **Security model**: summary; the details go to `docs/security.md` (Q3).
   13. **Shamsine**: how cards M.1–M.16 use this API (a table), the `expect` mapping (`text`, `number`, `boolean`, `date`, `dateTime`, `list` → Minab types), host inputs `currentUser`/`url`, the clock, one data port per application database.
   14. **Alternatives considered**: structured data requests (D28 b), several packages (D31 b), ESM only (D32 b), "edit vs. run" split (post-1.0).
   15. **Consequences**.
2. **A throwaway spike** in a scratch folder **outside the repository** (or a `spikes/` folder you delete before committing): (a) prepare and run one correlated rule with a fake data port inside a Vite Web Worker; (b) the same inside a NestJS app compiled to CommonJS; (c) 50 concurrent prepares and runs on one service set, checking every result. Write the findings and numbers into the ADR (Concurrency, Packaging). The goal is to find surprises (ES modules vs. CommonJS, bundle size, shared workspace state) before R2 commits to an API.
3. Set your status to **`waiting for approval`**. The owner reviews the ADR (helper prompt "Review a phase waiting for approval") and moves it to `done`.

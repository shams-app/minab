# P2 — Compile a group expression to a SQL fragment

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| P — Shamsine pivot | Mechanical | M | [P1](P1.md), [C10](C10.md), [Q3](Q3.md) | — | `next` channel, then the next release |

## Goal

A host can take a prepared group expression (P1) and get **one SQL expression** back, to place inside its own `SELECT … GROUP BY …`. For `SUM(.Revenue) - SUM(.Cost)` the host gets `SUM(<its SQL for Revenue>) - SUM(<its SQL for Cost>)`. The host's database then computes the expression for every group, including subtotals and the grand total, in the same statement as everything else.

## Why now

Shamsine's pivot builds one `GROUPING SETS` statement for the whole table. A calculated value must be part of that statement, so each cell uses its own rows (P1 explains why). Running the interpreter once per cell would need every cell's rows in the service, which is slow and big. `compile()` today makes a whole statement; the pivot needs only an expression.

## Ask first

All in one message, with these recommendations:

1. **Column mapping.** Proposed: the host gives a function `column(name: string): string` that returns the SQL of one column of the group row (for example `b.v_3`, or `(b.price)::numeric`). Minab calls it only with names that exist in `groupTable`, and puts the result in parentheses. Minab never writes a column or table name itself. Alternative: the host gives a plain table alias and Minab writes `alias."column"` from the schema's `sqlName`. The function is more flexible (the pivot reads computed and joined columns).
2. **Literals.** Proposed: always **inline**, never `$1` parameters: numbers as exact decimal text, text as a quoted literal with `'` doubled, `null`, booleans. The host puts the fragment in a statement that has its own parameters, so numbering would clash. The checked source limit (R4) already bounds the size.
3. **Type of the fragment.** Proposed: the fragment's SQL type is `numeric` for number results (no float, no rounding), and the host casts. `COUNT` is `bigint`. Documented in the card's Output.

## Build

1. **API.** `PreparedProgram.compileGroupExpression(options): CompileExpressionResult` where `options = { column: (name: string) => string }` and the result is `{ ok: true; sql: string } | { ok: false; error: MinabError }`. It refuses a program that is not a valid group expression (`error.code = "compile.notGroupExpression"`). Export the types from `src/runtime/index.ts`; the `exports` map has no new entry.
2. **Compile.** Reuse the compiler's expression code: arithmetic, `if`/`switch` as `CASE`, comparison and the built-ins (C2, C4, C9, C10 rules). Aggregates: `SUM(x)` → `SUM(<x>)`, `AVG` → `AVG`, `MIN`, `MAX`, `COUNT(.)` → `COUNT(*)`, `COUNT(<x>)` → `COUNT(<x>)`. `SUM` over an `INTEGER` expression keeps the exact integer rule of the existing compiler.
3. **Division by zero** as P1 decided: `a / b` → `a / NULLIF(b, 0)`, `%` and `\` the same. Nothing else changes.
4. **No statement text.** The fragment never has `SELECT`, `FROM`, a subquery, a semicolon or a comment. A test checks this for every case.
5. **Differential test.** Add a case file `test/differential/cases/p2-group-expression.cases.ts`: rows go to Postgres as a `VALUES` list; the fragment runs with `GROUP BY GROUPING SETS ((), (region), (region, month))`; the interpreter runs the same expression on the rows of each group. Both must agree on every group, including the grand total, an empty-looking group and a zero denominator (`null`). The existing harness gives the Postgres connection.
6. **Safety.** Add a fuzz file: random group expressions with hostile text literals (`'`, `\`, `--`, `;`, Unicode) never produce a fragment that changes the statement shape (the test wraps the fragment in `SELECT <fragment> FROM (VALUES …) v GROUP BY ()` and expects one row, or a coded error). The host-supplied `column()` output is trusted and documented as such (`docs/security.md`: one paragraph).
7. **Docs.** `docs/guides/shamsine.md`: the pivot example from SQL side, with the output for the three rows of P1. `docs/reference` API page for the new method.

## Output

`prepared.compileGroupExpression({ column })` → `{ ok, sql }`. A `next` prerelease of `@shamsine/minab` (D05) carries P1 and P2; its number goes to Shamsine's pivot card PX.4 and the monorepo bumps the dependency.

## Test scenarios

- `SUM(.Revenue) - SUM(.Cost)` with `column = n => "b." + n.toLowerCase()` gives `(SUM((b.revenue))) - (SUM((b.cost)))` (any equal-meaning form is fine; the test checks the run result, and the text only for shape rules).
- Over the sample rows, the grand total, each region and each (region, month) equal the interpreter's result.
- `SUM(.Price * .Units)` is `48` for the P1 sample rows, `SUM(.Price) * SUM(.Units)` is `161` (so the two programs differ).
- `SUM(.Profit) / SUM(.Revenue)` with a zero denominator gives `NULL`, the statement does not fail.
- `"it's"` in a text literal, a `;` and `--` inside a literal stay inside the literal.
- A group expression that fails P1's checks → `{ ok: false }`; a normal program → `compile.notGroupExpression`.
- `COUNT(.)` is `COUNT(*)`; an empty group gives `0`.

## Done when

All scenarios pass in the differential, query and fuzz suites on Postgres (CI job). `npm test`, lint and format pass. Docs are updated. The `next` prerelease with P1 and P2 is published by the normal workflow after the merge (the card does not publish).

## Not here

The interpreter and checker rules (P1). Any change in Shamsine (monorepo card PX.4 does that). Window functions, `FILTER (WHERE …)` and distinct aggregates.

## Later

`COUNT(DISTINCT …)` and `MEDIAN` as aggregates if Shamsine wants them in calculated values.

## If it grows

Move the fuzz file (step 6) to Later only if the differential cases show no quoting problem; keep step 6's one-paragraph security note either way.

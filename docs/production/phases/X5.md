# X5 — Writes, part 1: the write port and table writes

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| X — Execution | Design → Mechanical | M | [X3](X3.md), [H1](H1.md), [H7](H7.md) | [D26](../decisions.md#d26) | 0.4.0 |

## Goal

`INSERT`, `UPDATE` and `DELETE` on tables run through the write port as parameterized SQL, inside one transaction per run, with affected-row counts. The CLI shows a readable **dry run** by default and writes only with `--apply`. Validation rules cannot write.

## Why now

It is the only phase that can damage data, so it comes after statements (X3) and the Node adapters (H1). It waits for H7 because both change the playground engine. Shamsine's commands will run Minab code that writes.

## Build

1. **Write port**: `WritePort` with `transaction(async (tx) => …)`, and `tx.execute(query, { signal }) → { rowCount }`. Node implementations in `src/node/`: for `pg` (a client or pool: `BEGIN`/`COMMIT`/`ROLLBACK`) and for a query function with a host-provided transaction (TypeORM `QueryRunner`: the host starts and ends the transaction; Minab only executes).
2. **One run = one transaction** (D26): all writes of a run share one transaction; an error anywhere rolls back everything; the run result has `stats.writes` (statements and rows).
3. **Compiler**: `INSERT INTO … VALUES …` (from an object literal, a list of them, or a query: `INSERT … SELECT`); `UPDATE … SET …` with `SET` operators `:` (assign), `+:`/`-:`/`*:`/`/:` (relative), `:|` (merge into a `JSON` column, `||` in Postgres); `DELETE … WHERE …`; `ORDERBY`/`LIMIT` on `UPDATE`/`DELETE` via a key subquery (`WHERE id IN (SELECT id … ORDER BY … LIMIT …)`). Everything parameterized. Targets may also be relation paths that resolve to a table (`UPDATE .orders WHERE …`): compile with the foreign-key condition.
4. **Rules cannot write** (D26): the checker gives `rule.writeInRule` when a program used as a record or field rule (rule context) contains `INSERT`/`UPDATE`/`DELETE` or a record path assignment.
5. **Dry run**: `run(…, { writes: 'dry-run' | 'apply' })`. Dry run collects the statements without executing them (reads still run) and returns them in the result. The CLI defaults to dry run and prints a readable list (statement and parameters, as in D26's example); `--apply` writes. The runtime API has **no** default for hosts: they must choose (a missing choice is an error `eval.writeModeMissing`), so no host writes by accident.
6. **Examples**: `examples/order-dml` becomes runnable if it only uses table targets (else it waits for X6; say which). Its `expected.json` shows the dry-run output.
7. **Tests on Postgres** (`test/writes.test.ts`, PGlite and `MINAB_TEST_DATABASE_URL`): rows really change with `apply`; nothing changes with dry run; a failure in the third statement rolls back the first two; `rowCount`s are right; `LIMIT` on `DELETE` deletes the right rows.
8. **Playground**: a program with table writes runs in dry-run mode and shows its statements in the Execution tab; table writes leave the check-only list.
9. **Spec §10**: a short "How writes run" note (transactions, dry run, rules cannot write). README output blocks only if a checked one changes.

## Do not touch

`JSON`-array targets and record path assignment (X6).

## Output

Safe table writes for hosts and the CLI.

## Test scenarios

Listed in Build 7. Also: a field rule containing `DELETE` → `rule.writeInRule`; a run without a write mode → `eval.writeModeMissing`; the CLI without `--apply` changes nothing.

## Done when

Table writes run in both modes with transaction tests on Postgres; rules cannot write; the CLI defaults to dry run.

## Not here

`JSON`-array writes, ordinal targets, path assignment with `!` (X6).

## Later

None expected.

## If it grows

`INSERT … SELECT` and `ORDERBY`/`LIMIT` on `UPDATE`/`DELETE` may move to X6 with the owner's OK. Transactions, dry run and the rule check must stay.

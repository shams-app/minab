## Goal

The playground's worker and client run on the browser entry: `serveMinab` in the worker, `createWorkerMinab` on the UI thread. One message bridge, one error shape, one cancel path, for the playground and for apps. The engine keeps what only the playground needs (the Execution trace, the demo Postgres, the SQL console, editor intelligence), and it is now served through the bridge.

Owner decision, 2026-10-04: the card first said "thin layer over `createWorkerMinab`". That does not fit the code. The engine needs a data port and an event sink per run, column names and the syntax tree for its trace, and one schema per host. So this card (a) adds two small, general features to `src/browser/` (host requests and host events), and (b) moves the playground's own worker protocol onto them. Running the engine's programs through the bridge's `run` (per-run worker ports) is **not** in this card: it is listed under Later.

## Why now

The playground is the most-used host: if it runs on the published entry, every visitor tests it. E1 (`intel.ts`) and L7 (the Console's log transport) changed the playground engine first, so this phase does not collide with them.

## Build

1. **Bridge: host requests** (`src/browser/`). `serveMinab(endpoint, { requests })` takes a map `name -> (payload, { signal }) => value`. `WorkerMinab.request(name, payload?, { signal? })` calls one and answers with its value. A failure of the handler is `wire.requestFailed` (new code, message is the handler's own message). An abort sends `cancel` and rejects at once with `cancelled`; the handler's `signal` aborts.
2. **Bridge: host events.** `serveMinab` returns `emit(name, payload)`. `WorkerMinab.onEvent(listener)` receives them and returns an unsubscribe function.
3. **Bridge: one server per endpoint.** `serveMinab` on an endpoint that is already served replaces the earlier server. Without this, a worker file that imports `@shamsine/minab/browser/worker` would run two servers (the module starts itself in a Web Worker).
4. **Playground worker.** `worker.ts` calls `serveMinab(self, { requests })`. The requests are the `EngineApi` methods. Engine status goes out as the `status` event. The messages of `engine/protocol.ts` that only carried this (`EngineRequest`, `EngineResponse`, `EngineEvent`, `EngineMessage`) are removed.
5. **Playground client.** `engine-client.ts` is a thin layer over `createWorkerMinab`: `call`, `onStatus`, `restart` as today (calls in flight fail with "the engine was restarted"). `run` can be cancelled: the engine stops the program at the next check, and the controller cancels the run it replaces.
6. **Docs and tests.** `src/browser/README.md` (the playground now uses the entry), `test/browser/` tests for requests, events, cancel and the replace rule, a playground test that drives `EngineClient` and the worker over a `MessageChannel`.
7. **Bundle.** Compare the playground's production bundle size before and after; write both in your status file. It must not grow by more than 5%.

## Do not touch

`playground/src/ui/**`, the bridge messages that exist (`create`, `prepare`, `compile`, `run`, `editor`, `cancel`, `release`, `dispose`, `port-*`): the bridge stays version 1.

## Output

One bridge for the playground and for apps. Hosts that keep their own work in the worker get `requests` and `events`.

## Test scenarios

- The playground suite passes unchanged (only new tests are added).
- A request returns its value; an unknown request and a throwing handler give `wire.requestFailed`; an abort rejects with `cancelled` and aborts the handler's signal.
- An event reaches `onEvent`; the unsubscribe function stops it.
- A second `serveMinab` on one endpoint replaces the first (one answer per request).
- `EngineClient` over a message channel: `analyze` and `run` work, status events arrive, `restart` rejects calls in flight with "the engine was restarted", and a cancelled `run` stops.
- A manual check (`npm run dev`): run a gallery example, cancel a long run, restart the engine. Write the result in your status file.

## Done when

The playground worker and client run on `serveMinab` and `createWorkerMinab`, tests and build are green, the bundle did not grow by more than 5%.

## Not here

Design changes (W2, W3). Running the engine's programs through the bridge's `run` with per-run worker ports.

## Later

- Per-run worker ports (`ports` as a function of the run), column names in the data port result, and a `run` answer that carries host data, so the engine can execute through the bridge's `run` — next card.

## If it grows

The cancel of a running program (build step 5) may move to Later. Steps 1 to 4 must stay.

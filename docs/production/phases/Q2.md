# Q2 — Release automation and the `next` channel

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| Q — CI, release and quality | Mechanical | M | [Q1](Q1.md) | [D03](../decisions.md#d03), [D04](../decisions.md#d04), [D05](../decisions.md#d05) | 0.2.0 |

## Goal

A release is one tag push. The tag publishes the npm package (with provenance when the repository is public; D04 keeps it private, so none for now), builds the `.vsix`, creates the GitHub release with the CHANGELOG section as notes, and publishes the extension to the Marketplace and Open VSX. Every merge to `main` can publish a `next` prerelease. Changelog fragments become a CHANGELOG section with one command.

## Why now

The first release (V1) should already go out the automated way, and Shamsine needs `next` prereleases to integrate early.

## Read

- `package.json` (`version`, `scripts`, `prepack`, `files`, `publishConfig`), `vscode-extension/package.json`
- `CHANGELOG.md`, `vscode-extension/CHANGELOG.md`, `changes/README.md`
- `test/release.test.ts`
- `.github/workflows/` (the files Q1 and A1 made)
- Decisions D03, D04, D05

## Ask first

Which secrets exist in the repository settings: npm **trusted publishing** set up for this repository (preferred, no token) or `NPM_TOKEN`; `VSCE_PAT`; `OVSX_PAT`? (Recommended: trusted publishing for npm. The workflow must skip a missing one with a clear message, not fail without saying why.)

## Build

1. **`scripts/changelog.mjs`**:
   - `--version X.Y.Z [--date YYYY-MM-DD]`: reads every `changes/*.md` (front matter `type`, `scope`, `breaking`), writes a new `## [X.Y.Z] - date` section at the top of `CHANGELOG.md` in Keep a Changelog order (Added, Changed, Deprecated, Removed, Fixed, Security). Fragments with `scope: playground` go under a "Playground" heading at the end of the section. `breaking: true` entries start with **Breaking:**. Adds the `[X.Y.Z]: …/releases/tag/vX.Y.Z` link. Writes a shorter section to `vscode-extension/CHANGELOG.md` with only the scopes `language`, `editor`, `vscode`. Deletes the fragments it used.
   - `--check`: validates every fragment (front matter present, known `type` and `scope`). Add it as a step in `.github/workflows/plan.yml` (A1's file; add only that step).
   - `--notes X.Y.Z`: prints that version's CHANGELOG section (for the GitHub release body).
2. **`scripts/bump-version.mjs X.Y.Z`**: sets the version in `package.json` and `vscode-extension/package.json` and their lockfiles (`npm version X.Y.Z --no-git-tag-version` in both).
3. **`scripts/next-version.mjs`**: prints the prerelease version for a build: if `package.json`'s version is already published on npm, `<next minor>-next.<run number>` (for example `0.3.0-next.42`), else `<version>-next.<run number>`.
4. **`.github/workflows/release.yml`** on a `v*` tag, and on `workflow_dispatch` with a `dry-run` input:
   1. check that the tag equals `v` + `package.json` version;
   2. `npm ci`, build, the full test suite including the Postgres service;
   3. `npm publish --access public`, with `--provenance` when the repository is public (`github.event.repository.private == false`); in a dry run, `npm publish --dry-run`;
   4. build the `.vsix` and run Q1's `check:vsix`;
   5. create the GitHub release with `scripts/changelog.mjs --notes`, attach the `.vsix`;
   6. `npx @vscode/vsce publish` if `VSCE_PAT` exists, `npx ovsx publish` if `OVSX_PAT` exists (D04); otherwise print "skipped: secret not set".
5. **`.github/workflows/next.yml`** (only if D05 = yes) on push to `main`, skipped when only `docs/**`, `playground/**` or `*.md` changed: build, test, set the version from `next-version.mjs` (in the CI workspace only; never committed), `npm publish --tag next --access public` (provenance when public).
6. **`docs/releasing.md`**: the human checklist the V phases follow: choose the version, run `changelog.mjs` and `bump-version.mjs` on a `release/vX.Y.Z` branch, open a PR titled `[V…] Release X.Y.Z`, merge, push the tag (the owner, or a session the owner told to), watch `release.yml`, verify from a clean machine (`npx @shamsine/minab@X.Y.Z --version`), check the Marketplace and Open VSX pages, do the manual VS Code check. Say that the GitHub release and its `.vsix` are visible only to repository members (D04: the repository stays private); the public places are npm, the Marketplace and Open VSX.
7. Unit tests for the three scripts in `test/release-scripts.test.ts`, using temporary folders.

## Files

`scripts/changelog.mjs`, `scripts/bump-version.mjs`, `scripts/next-version.mjs` (new), `test/release-scripts.test.ts` (new), `.github/workflows/release.yml`, `.github/workflows/next.yml` (new), `.github/workflows/plan.yml` (one step), `docs/releasing.md` (new).

## Do not touch

`CHANGELOG.md` and the version numbers (V1 runs the scripts for real).

## Output

The V phases release with: scripts on a branch, a PR, a tag. Shamsine can install `@shamsine/minab@next`.

## Test scenarios

- `changelog.mjs`: three fragments (an added, a fixed, a breaking change in `runtime`, plus one `playground`) → the expected section text, in order, with the Playground heading and the Breaking prefix; the fragments are deleted; the extension changelog gets only matching scopes.
- `changelog.mjs --check` fails on a fragment with no `type`, or an unknown `scope`.
- `next-version.mjs`: version `0.2.0` not published, run 7 → `0.2.0-next.7`; published → `0.3.0-next.7` (mock the npm lookup).
- `bump-version.mjs 0.2.1` changes both package files and keeps the release metadata test green.
- The owner (or you, if the session may) runs `release.yml` with `dry-run: true` from the Actions tab on this branch: it goes green. Put the run link in your status file.

## Done when

The scripts are tested; `release.yml` passed a dry run; `next.yml` exists (if D05 = yes) and its first run after merge is reported by the owner; `docs/releasing.md` is written.

## Not here

The first real release (V1). The extension's Marketplace polish (E4).

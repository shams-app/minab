# A1 — Plan bootstrap: AI entry file, rules, fragments and guards

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| A — Start | Mechanical | S | — | — | — |

## Goal

The repository is ready for many AI sessions working at the same time: one entry file Claude Code reads first, rules that point at this plan, a folder for changelog fragments, a guard that stops a pull request from editing files it must not edit, and a workflow that rebuilds the progress page after each merge.

## Why now

Every other phase follows these rules. It touches files no other phase owns, so it can run next to A2.

## Read

- `docs/production/README.md` (all of it: this is the rulebook you are installing)
- `docs/production/tools/progress.mjs` (only the usage comment at the top)
- `.cursor/rules/00-project-overview.mdc`, `.cursor/rules/language-implementation.mdc`, `.cursor/rules/spec-governance.mdc`
- `docs/status.md` (only the "Current status" and "Next job" sections), the first 30 lines of `docs/roadmap.md`
- `package.json` (`files`), `test/release.test.ts`, `.github/workflows/ci.yml` (for style only)

## Ask first

None.

## Build

1. **`CLAUDE.md`** at the repository root, short (under 60 lines):
   - import the three rule files with `@.cursor/rules/00-project-overview.mdc`, `@.cursor/rules/language-implementation.mdc`, `@.cursor/rules/spec-governance.mdc`;
   - "Work on this repo follows the production plan: read `docs/production/README.md` before any phase";
   - house rules: npm only (no bun or yarn); the playground and the extension are separate npm packages with their own `node_modules`; never edit `src/language/generated/`; run the playground tests after any change under `src/`;
   - "Write for a reader whose first language is not English: short sentences, simple words."
2. **`.cursor/rules/00-project-overview.mdc`**: add a short section "Working on the production plan" (3–6 lines): the plan lives in `docs/production/`; one status file per phase; changelog fragments in `changes/`; protected files are listed in `docs/production/README.md`. Change nothing else in this file (L1 owns the lines about `&`).
3. **`.cursor/rules/language-implementation.mdc`**:
   - replace the paragraph that starts "Current implementation status (update this line as work lands…" with two lines: what is done lives in `docs/production/progress.md` and in each phase's status file; do not keep a running status line here;
   - add the **folder README rule**: every new folder under `src/`, `test/` or `examples/` gets a `README.md` that lists its files and rules; when you change a folder, update its README, not this file;
   - mark the existing "Layout" list as "as of 2026-10-01; newer folders describe themselves in their own README".
4. **`docs/status.md`**: replace the "Current status" and "Next job" sections with one short paragraph: this log is closed on the date of this phase; status now lives in `docs/production/progress.md` and `docs/production/status/`. Keep the whole session log below it unchanged. Change the first line under the title so it no longer says "update the top two sections every session".
5. **`docs/roadmap.md`**: add one line under the title pointing to `docs/production/README.md` as the plan after Phase 9. Change nothing else.
6. **`changes/README.md`**: the changelog fragment rules and the template, copied from `docs/production/README.md` ("Changelog fragment format").
7. **Package contents**: in `package.json` `files`, add `"!docs/production/**"` and `"!docs/release-future/**"`, so the plan never ships in the npm package. In `test/release.test.ts` ("npm tarball contents"), assert that no packed path starts with `docs/production/` or `docs/release-future/`.
8. **The guard**: `scripts/plan-guard.mjs`, a small Node script with no dependencies. Input: the pull request title and the list of changed files (arguments or stdin). It fails (exit 1, with a clear message per file) when:

   | Changed file | Allowed only when the PR title starts with |
   |---|---|
   | `CHANGELOG.md`, `vscode-extension/CHANGELOG.md` | `[V1]`, `[V2]`, `[V3]`, `[V5]` |
   | `README.md` (root) | `[V1]`–`[V5]`, `[G1]`, and (for checked output blocks only) `[C2]`, `[C3]`, `[C4]`, `[C6]`, `[R7]`, `[L7]`, `[X4]`, `[X5]`, `[X6]` |
   | `docs/status.md`, `docs/roadmap.md` | `[A1]`, `[V1]` |
   | `docs/production/progress.md` | never in a phase PR |
   | `docs/production/README.md`, `docs/production/phases/**` | `[A2]` |
   | `docs/production/status/<X>.md` | `[X]` (a PR changes only its own status file) |
   | `changes/<X>*.md` added or changed | `[X]`; release PRs (`[V…]`) may delete any fragment |
   | `.github/workflows/ci.yml` | `[Q1]` |

   A PR whose title has no `[ID]` prefix is the owner's own PR: everything is allowed, and the script prints a notice.
9. **`.github/workflows/plan.yml`** (new file):
   - on `pull_request`: `node docs/production/tools/progress.mjs --check`, then the guard with the PR title and `git diff --name-only origin/<base>...HEAD`;
   - on `push` to `main` (paths `docs/production/**`): `node docs/production/tools/progress.mjs --write`; if `progress.md` changed, commit it as `github-actions[bot]` with the message `docs(plan): update progress [skip ci]` and push (`permissions: contents: write`). Mark the push step `continue-on-error: true` (branch protection may forbid it) and always append `progress.md` to `$GITHUB_STEP_SUMMARY`, so the graph is visible in the run either way.
10. **`.github/pull_request_template.md`**: phase ID and title; "Depends checked"; "status file written"; "changelog fragment written or not needed"; "checks run (paste counts)"; "no protected file edited outside my card".

## Do not touch

Source code, the spec, the showcase, `docs/production/**` except `status/A1.md`. (`progress.md` already exists; the workflow keeps it fresh from now on.)

## Output

- `CLAUDE.md`: every later session reads the rules automatically.
- `changes/`: the place for fragments.
- The guard and the plan check run on every pull request; the progress page updates itself after merges.

## Test scenarios

- `test/plan-guard.test.ts` (unit tests of the script):
  - `[C3]` changing `CHANGELOG.md` → fails; `[V1]` → passes;
  - `[C3]` adding `docs/production/status/C3.md` → passes; also adding `status/C4.md` → fails;
  - `[C3]` adding `changes/C3.md` → passes; adding `changes/C4.md` → fails;
  - `[V2]` deleting `changes/C3.md` → passes;
  - a title without `[ID]` changing anything → passes with a notice;
  - `[Q2]` changing `.github/workflows/ci.yml` → fails; `[Q1]` → passes.
- `test/release.test.ts`: remove the `!docs/production/**` entry from `files` locally → the test fails; put it back → it passes.
- `node docs/production/tools/progress.mjs --check` exits 0.

## Done when

- All the files above exist and `npm run build && npm test` is green (the playground suite too, if you touched anything it builds).
- The plan check and the guard run in `plan.yml` on this PR and pass.
- `npm pack --dry-run` lists nothing under `docs/production/` or `docs/release-future/`.

## Not here

- Test and release CI jobs (Q1, Q2). Lint (B1).
- Changing what the rules *say* about the language (spec governance stays as it is).

## Later

None expected.

## If it grows

It should not. If the bot commit on `main` is not possible (branch protection), keep the job summary and write in your status file that the owner runs `node docs/production/tools/progress.mjs --write` after merges.

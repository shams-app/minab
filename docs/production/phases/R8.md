# R8 — The playground engine runs on the runtime API

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| R — Runtime | Mechanical | M | [R4](R4.md), [R5](R5.md) | — | 0.3.0 |

## Goal

The playground's engine (in its Web Worker) checks, compiles and runs programs through `createMinab`/`prepare`/`run`, uses the event stream for its Execution tab and the analysis for its program info, and keeps its message protocol so the UI does not change.

## Why now

The playground is the second real host and the closest to Shamsine's browser use. Its engine becomes the base of the published browser runtime (H4).

## Read

- `playground/src/engine/engine.ts`, `language.ts`, `program.ts`, `protocol.ts`, `worker.ts`, `database.ts`, `intel.ts` (only how it gets documents)
- `playground/src/client/engine-client.ts`
- `src/runtime/` (README, `index.ts`, `analyze.ts`)
- `playground/test/engine.test.ts`, `playground/test/content.test.ts`

## Ask first

None.

## Build

1. `engine.ts` and `language.ts` use the runtime API: one `Minab` per host settings (schema + rule context), `prepare` for `analyze`, `compile()` for the SQL tab, `run` with a PGlite `DataPort` (from `database.ts`) or the fixture data port, and the event sink for the Execution tab (statement events with source ranges).
2. Program kind and "check-only constructs" come from the runtime (`kind`, and analysis `writes`/constructs) instead of the playground's own code where the runtime has it. Keep `protocol.ts` types stable; adapt inside the engine.
3. `intel.ts` keeps working (E1 will move its logic): give it the prepared document the runtime keeps, or keep its own parse for now (say which in your status file).
4. Remove R4's compatibility adapter if R7 has already merged.
5. The playground suite (every gallery example and tour lesson) passes unchanged; the bundle still builds.

## Files

`playground/src/engine/engine.ts`, `language.ts`, `program.ts`, `worker.ts`, `database.ts` (data port shape), possibly `intel.ts`; `playground/test/engine.test.ts` (only where internals changed).

## Do not touch

`playground/src/ui/**`, `playground/src/state/**`, content. `protocol.ts` types (keep them stable).

## Output

The playground on the public API; a worker engine ready to generalize (H4).

## Test scenarios

- Every playground test passes; every gallery example gives its expected result.
- The Execution tab data (statement ranges) is identical for three gallery examples (compare before and after in a test).
- `npm run build` in `playground/` succeeds; note the bundle size before and after in your status file.

## Done when

The engine uses only `src/runtime/` (plus `src/host/` and its own database code) for language work; tests and build green.

## Not here

The published browser worker (H4), editor services (E1), UI changes.

## Later

None expected.

## If it grows

Moving `intel.ts` fully may wait for E1. Everything else is required.

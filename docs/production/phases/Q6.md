# Q6 — A real release runs only from a version tag

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| Q — CI, release and quality | Mechanical | S | [Q2](Q2.md) | [D04](../decisions.md#d04) | 0.4.0 |

## Goal

`release.yml` publishes only when it runs on a tag `v<version>` that matches `package.json`. A hand-started run with `dry-run` off on a branch stops at once with a clear message, before it builds or publishes anything. The GitHub release step never creates a tag.

## Why now

The 0.2.0 release needed manual repair (V1 status). A hand-started run on `main` with `dry-run` off published from the branch, and `gh release create "$GITHUB_REF_NAME"` made a release and a tag named `main`. The owner deleted both and made `v0.2.0` by hand. The V1 and V2 Later lists ask for this fix, and the workflow still allows it on 2026-10-11. V4 point 8 needs "the last two releases went through `release.yml` without manual steps". So V3 (0.4.0) must run on the fixed workflow.

## Build

1. **A guard script.** Add `scripts/release-guard.mjs` (and its `.d.mts`, like the other scripts). Its inputs are the ref type, the ref name, the `package.json` version and the dry-run flag. It prints what the run will do, or fails with a clear message. The rules:
   - A dry run is allowed on any ref.
   - A real run (a tag push, or a hand-started run with `dry-run` off) is allowed only on the tag `v<version>`.
   - A hand-started run on that tag with `dry-run` off is allowed: it is how to run a failed release again.
2. **The workflow.** `release.yml` calls the script as its first step after checkout, in place of today's tag check. A run the script refuses stops before `npm ci`.
3. **The GitHub release.** `gh release create` takes the tag `v$VERSION` and `--verify-tag`, so it never makes a tag.
4. **Docs.** In `docs/releasing.md`: a real release is a tag push. To run a failed release again, start **Release** on the tag with `dry-run` off. Never start it with `dry-run` off on a branch. Also update `scripts/README.md`.

## Files

`scripts/release-guard.mjs` (new), `scripts/release-guard.d.mts` (new), `.github/workflows/release.yml`, `test/release-scripts.test.ts`, `docs/releasing.md`, `scripts/README.md`.

## Do not touch

`.github/workflows/ci.yml` (Q1 only). `next.yml` (the `next` channel already publishes only from `main`, as a prerelease).

## Output

A release workflow that cannot publish from a branch.

## Test scenarios

In `test/release-scripts.test.ts`, with the version `0.4.0`:

- A tag push `v0.4.0`: allowed, a real run.
- A tag push `v0.4.1`: refused (the tag does not match the version, as today).
- A hand run on `main` with `dry-run` on: allowed, a dry run.
- A hand run on `main` with `dry-run` off: refused, and the message says a real release runs only from a version tag.
- A hand run on the tag `v0.4.0` with `dry-run` off: allowed (a second try of a failed release).
- A hand run on the tag `foo` with `dry-run` off: refused.

## Done when

- Every scenario passes.
- `release.yml` uses the script, and `gh release create` has `--verify-tag`.
- A dry run of **Release** on this branch passes. Start it yourself if the session can (the GitHub tools), and link the run in your status file. If it cannot, write that in your status file: V3 runs the dry run before its tag anyway.
- `docs/releasing.md` is updated.
- No changelog fragment: this is a CI change only.

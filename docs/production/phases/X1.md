# X1 — Queries accept `switch`, `if`, `is` and JSON literals

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| X — Execution | Mechanical | M | [C1](C1.md) | — | 0.4.0 |

## Goal

Ordinary expressions that work outside a query also work inside one: `switch` and `if` become `CASE`, `is`/`isnot` become `IS NULL` and `jsonb_typeof` tests, JSON object and list literals become `jsonb_build_object`/`jsonb_build_array`, and `FROM` can start from a filtered related collection.

## Why now

These pass `check` today and then refuse to run inside a query. They are ordinary spec constructs (§5.6, §9.2). C1's query harness proves the compiled forms on Postgres.

- `src/language/minab-sql-compiler.ts`: `expression()` (the refusals for `SwitchExpr`, `TypeTestExpression`, `JsonObjectLiteral`), `sourceTable()`/`scopeOf()` (the `FROM .orders[...]` refusal)
- Spec §5.6, §7.3, §9.1, §9.2, §3.2

## Ask first

None.

## Build

1. **`switch`** → `CASE <subject> WHEN … THEN … ELSE … END` (or `CASE WHEN … = …` when a case value is `null`, since `= NULL` never matches). Arms with a `Block` that has statements refuse with `compile.blockInQuery` (a statement cannot run inside SQL); a block with only a tail is fine.
2. **`if` expressions** → `CASE WHEN … THEN … ELSE … END`; no `else` → `ELSE NULL`. Same rule for blocks.
3. **`is` / `isnot`**: `x is null` → `x IS NULL`; for `JSON` values, `is object/array/string/number/boolean` → `jsonb_typeof(x) = 'object'` and so on (match spec §5.6 exactly: check the five kinds it names).
4. **JSON literals** → `jsonb_build_object(k1, v1, …)` and `jsonb_build_array(…)`, nested as needed; values bound as parameters.
5. **`FROM .orders[.status == "x"]`** (a filtered related collection as the source) compiles to `FROM "Order" AS … WHERE <fk> = <outer key> AND <filter>`.
6. For each: an expected-SQL test in `test/sql-compilation.test.ts` and a run on Postgres in `test/queries/cases/x1-*.cases.ts`; scalar cases in `test/differential/cases/x1-*.cases.ts` (interpreted vs compiled).
7. Playground: any gallery example or cheat-sheet note that says these do not work in a query is updated.

## Files

`src/language/minab-sql-compiler.ts`, `src/language/diagnostics/codes.ts`, `test/sql-compilation.test.ts`, query and differential case files, playground content where it mentions the limitation.

## Do not touch

Multi-key `KEY` and user functions in queries (X2).

## Output

Queries that accept the whole expression language (except statements).

## Test scenarios

- `FROM Order SELECT switch (.status) { "a" => 1, _ => 2 } AS s` runs and agrees with the interpreter row by row.
- `FROM Order WHERE .customer is null SELECT .id AS id` returns the orders with no customer.
- `FROM Order SELECT { id: .id, t: .total } AS o` returns JSON objects.
- `FROM Event WHERE .payload is array …` (a `JSON` column) works.
- `FROM .orders[.status == "x"]` inside a customer rule returns the right rows.
- A `switch` arm with a statement inside a query → `compile.blockInQuery`.

## Done when

Each construct compiles and runs on Postgres, with tests; the refusals left are statement blocks only, with a stated reason.

## Not here

`KEY` with several keys; user functions in queries (X2).

## Later

None expected.

## If it grows

It should not.

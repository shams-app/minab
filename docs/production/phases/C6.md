# C6 — `check` accepts a top-level collection filter

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| C — Correctness | Mechanical | M | [L1](L1.md) | — | 0.2.0 |

## Goal

A rule like `COUNT(.orders[.status == "cancelled"]) < 5` (showcase §1's own example) passes `check` and runs. The examples and playground programs that were written around this bug go back to their natural form.

## Why now

`check` is the contract the CLI, the language server, the playground and Shamsine's save-time validation all rely on. Rejecting a valid program is a broken promise. It waits for L1 because both edit the playground gallery.

## Read

- `src/language/minab-scope-resolver.ts` (how a `.field`-rooted receiver finds its table: `tableOfExpression`, `followRelationColumn`)
- `src/language/minab-type-checker.ts`: `rootFallbackTable` (the checker already knows `rule.recordTable`; the resolver does not)
- `src/language/minab-module.ts` (how services get `MinabRuleContext`)
- `examples/cancelled-orders-limit/`, `examples/overdue-loop/`
- `playground/src/content/examples/index.ts` (search for `COUNT(#Order[.customer == ^`)
- `test/evaluation.test.ts` (it calls the interpreter without the validator, which is why the bug went unseen)

## Ask first

None.

## Build

1. Give `MinabScopeResolver` the rule context's `recordTable`, so a top-level `.orders[...]` resolves `.orders` against the record's table and the filter's `.status` against `Order`.
2. Regression tests **at the `check` level** (validator + checker), not only in evaluation: the showcase §1 rule, a nested filter (`.orders[.items[.qty > 2]]`), and a field rule using `$` next to a filter.
3. A CLI test: `minab check` on a file with that rule and a config with `rule.recordTable` reports no problems; `minab run` gives the documented answer.
4. **Revert the workarounds**:
   - `examples/cancelled-orders-limit`: back to the `COUNT(.orders[.status == "cancelled"]) < 5` form; update its `expected.json` (statement count may change: write the real number and check it is the expected strategy);
   - `examples/overdue-loop`: iterate `.orders` instead of `#Order` (it stays check-only until X4);
   - the playground gallery's `COUNT(#Order[.customer == ^ …])` forms → the natural `.orders[...]` form; the playground tests must still pass.
5. Fragment: `type: fixed`.

## Files

`src/language/minab-scope-resolver.ts`, `src/language/minab-module.ts` (if wiring changes), tests (`test/typechecking.test.ts` or a new `test/collection-filter.test.ts`, `test/cli.test.ts`), two examples and their `expected.json`, `playground/src/content/examples/index.ts`, README output blocks only if a checked one changes.

## Do not touch

The type checker's other rules.

## Output

`check` tells the truth for collection filters in rules.

## Test scenarios

- The showcase §1 rule checks clean with `recordTable: Customer`, and runs.
- Without `recordTable`, the error message stays as clear as today.
- A filter on a relation of a relation (`.customer.orders[...]`) checks.
- The reverted examples check and give their documented answers.

## Done when

Showcase §1's rule passes `check` and runs; the examples and gallery use the natural forms; root and playground green.

## Not here

`GROUPBY` on a related field (C7). Loops running (X4).

## Later

None expected.

## If it grows

It should not.

# B1 — Diagnostic codes, format and lint, one expected-result file per example

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| B — Code-wide sweep | Mechanical | M | [A1](A1.md), [A2](A2.md) | [D08](../decisions.md#d08), [D35](../decisions.md#d35), [D09](../decisions.md#d09) | 0.2.0 |

> **Runs alone.** This phase touches almost every source file. Start no other *code* phase until it is merged. Docs and design phases (R1, W1) and CI (Q1) may run next to it.

## Goal

Three sweeps that touch many files, done once before the lanes open:
1. every diagnostic from the checker gets a **stable code** and parameters, so hosts (Shamsine) can translate messages;
2. the code base is **formatted** once and **linted** in CI;
3. each example's expected result moves into **its own file**, so later phases that change different examples never edit the same test file.

## Why now

Done later, each sweep would collide with every running phase. Done now, later phases only add to it.

- `src/language/minab-validator.ts` (every `accept(...)` call), `src/language/minab-type-checker.ts` (`TypeResult`, `err(...)`), `src/language/minab-scope-resolver.ts` (failure reasons)

## Build

1. **Code registry** — `src/language/diagnostics/codes.ts` (+ a `README.md` in that folder):
   - one entry per diagnostic: `code`, `severity`, `message(params)` (today's English text, word for word, so existing message assertions still pass), and `doc` (one sentence that explains the problem and the fix);
   - codes are `<area>.<camelCaseName>`. Areas: `syntax`, `scope`, `type`, `null`, `call`, `query`, `rule`. Examples: `scope.unknownAlias`, `type.implicitCoercion`, `type.collectionAsScalar`, `null.orderingWithNull`;
   - keep the entries sorted by code (later phases insert without colliding);
   - a code never changes meaning once released (D38).
2. **Use it everywhere a checker diagnostic is made**: every `accept(...)` in the validator passes `code` and `data: { params }`. `TypeResult` and the resolver's failure results carry `code` and `params` next to today's `reason` (the reason stays the English message). Lexer and parser errors are reported with `syntax.lexer` / `syntax.parser` (map them in one place).
3. **Show the code** where tools read it: `minab check --json` adds `"code"` to each diagnostic (human-readable output stays exactly as today); the language server sends it (Langium does this when `code` is set: check it); the playground's `EngineDiagnostic` gets an optional `code` (no UI change).
4. **Reference page**: `scripts/diagnostics-doc.mjs` writes `docs/reference/diagnostics.md` (code, severity, message pattern, explanation), run by `npm run docs:diagnostics`. A test fails when the page is out of date.
5. **Formatter and linter** (if D08 = yes):
   - `.prettierrc.json` matching today's style (4-space indent, single quotes, semicolons). Try `printWidth` 120, 140 and 160 and keep the one with the smallest diff. `.prettierignore`: `out/`, `node_modules/`, `src/language/generated/`, `**/dist/`, all `*.md` (the spec is a controlled file), JSON fixtures.
   - `eslint.config.js` (flat config) with typescript-eslint type-aware rules, kept small: `no-floating-promises`, `no-misused-promises`, `await-thenable`, `no-unused-vars` (error), `consistent-type-imports`. Fix every finding. A real bug: fix it and add a test. A false positive: disable that line with a comment that says why.
   - Scripts: `lint`, `format`, `format:check` in the root `package.json` (covering `src/`, `test/`, `scripts/`, `vscode-extension/src/`). The playground gets Prettier only (`format`, `format:check` in its own `package.json`); its ESLint comes with W2.
   - Commit the one-time format **alone** (`chore: format with prettier`) and add that commit's hash to `.git-blame-ignore-revs`.
   - New workflow `.github/workflows/lint.yml`: `npm ci`, `npm run lint`, `npm run format:check`, and the playground's `format:check`.
6. **Example expectations**: move each entry of `MANIFEST` in `test/examples.test.ts` into `examples/<name>/expected.json`:
   - a run example: `{ "mode": "run", "json": …, "statements": n, "compiles": true|false }`;
   - a check-only example: `{ "mode": "check-only", "refusal": "<regular expression source>" }`.

   `test/examples.test.ts` reads every `examples/*/expected.json`. **Rule:** a folder in `examples/` that contains `<folder name>.minab` must have `expected.json`, or the test fails (the drift guard stays). Folders without a `.minab` program of that name (later: `examples/nestjs`, `examples/browser`) are ignored. Write this rule into a new `examples/README.md`.

The format commit touches many more files; it does not count toward the budget.

## Do not touch

Behavior. No message text changes, no new checks, no runtime (interpreter, compiler) error codes (R4 does those). The spec and showcase.

## Output

- Every checker diagnostic has a code; the registry and `docs/reference/diagnostics.md` list them.
- `npm run lint` and `npm run format:check` exist and run in CI.
- Later phases add an `expected.json` per example instead of editing a shared manifest.

## Test scenarios

- `test/diagnostic-codes.test.ts`: one small program per registry entry; the expected code appears on the diagnostic. A registry entry with no program fails the test (no dead codes).
- An existing type-check test, extended: the diagnostic for comparing `TEXT` with `INTEGER` has code `type.implicitCoercion` and params naming both types.
- `minab check --json` on a file with a type error prints `"code": "type.implicitCoercion"`.
- The language server diagnostic carries the code (`test/lsp.test.ts` or a validation helper test).
- Delete `examples/first-query/expected.json` locally → the examples test fails; restore it.
- Edit a registry entry's doc text without running `npm run docs:diagnostics` → the reference test fails.
- `npm run lint` passes. Add a floating promise in a scratch file → lint reports it; remove the file.

## Done when

- Every checker diagnostic has a registry code; the reference page is generated and checked.
- Format and lint are in CI and green.
- Example expectations are one file per example, and the examples test passes unchanged in what it checks.
- Root, playground and extension builds and tests are green.

## Not here

- Run-time and compile-time error codes (R4). Translations (never shipped, D35). Showing codes in the playground UI (W2) or in human CLI output (E3 may add it).

## Later

- Playground ESLint (W2).

## If it grows

The format and the expectations parts are small. If lint finds many style-only problems, turn those rules off (list them under Later) and keep the bug-finding rules. Never leave lint or format red.

# Q5 — Compatibility guard: language version and golden corpus

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| Q — CI, release and quality | Mechanical | S | [R2](R2.md), [V1](V1.md) | [D34](../decisions.md#d34), [D38](../decisions.md#d38) | 0.3.0 |

## Goal

Programs that hosts store (Shamsine keeps every expression in its database) keep working across Minab releases, or fail with a clear message and a migration path. A test proves it on every change.

## Why now

0.2.0 (V1) is the first version anyone can store programs for. From here on, a silent change in meaning would break real data.

## Read

- `src/runtime/` README and `prepare` (from R2)
- `docs/production/status/V1.md` (what was released)
- Decisions D34, D38

## Ask first

None.

## Build

1. **Language version**: export `LANGUAGE_VERSION` from the runtime (an integer; `1` for the language of 0.2.0). It goes up only when the meaning of valid programs changes or a form is removed. `prepare(source, { languageVersion })`:
   - newer than the runtime → diagnostic `compat.newerLanguage`;
   - older → run the migrations between the two versions, then check;
   - missing → the current version.
2. **Migrations**: `src/runtime/migrate.ts` with `migrate(source, fromVersion, toVersion)` and a list of migrations (`{ from, to, describe, transform(source) }`). The list is empty today. Test the framework with a fake migration in the test file.
3. **Deprecations**: registry area `deprecated` (codes `deprecated.*`, severity warning). Document the rule from D38: a deprecated form warns for at least one minor release before it is removed in a major.
4. **Golden corpus**: `test/compat/corpus/0.2.0/` with programs (`*.minab`), one `schema.json`, and `expected.json` (for each program: check result as codes, and run result for programs that run on a fixture). Build it from the `v0.2.0` tag's spec examples, showcase examples and `examples/`. The test runs every corpus folder against today's code and expects the same codes and results.
   - `npm run compat:snapshot <version>` creates a new corpus folder from the current code. Release phases V2, V3 and V5 run it.
   - An intentional change (only before 1.0, with a migration note) updates the expectation and is listed in that release's CHANGELOG.
5. **`docs/compatibility.md`**: the policy (D38), how hosts store `languageVersion` next to each program, what happens when it is older or newer, and how migrations will work.

## Files

`src/runtime/index.ts` (export), `src/runtime/prepare.ts` (option), `src/runtime/migrate.ts` (new), `src/language/diagnostics/codes.ts` (two codes), `test/compat/*` (new), `scripts/compat-snapshot.mjs` (new), `package.json` (script), `docs/compatibility.md` (new).

## Do not touch

The language itself.

## Output

`LANGUAGE_VERSION`, `migrate`, a corpus test that release phases extend.

## Test scenarios

- A corpus program changed on purpose → the test fails and names the program.
- `prepare` with `languageVersion: 99` → `compat.newerLanguage`.
- The fake migration rewrites a program from version 0 to 1 and the result checks clean.

## Done when

Corpus 0.2.0 exists and passes; the snapshot script works; the docs page exists.

## Not here

Real migrations (none needed yet).

## Later

A `minab migrate` CLI command once the first real migration exists (post-1.0 list).

## If it grows

It should not.

## Goal

A program can print values while it runs, like `console.log`: `LOG(value, label?)` records a value and returns it unchanged. A bare call can stand alone as a statement (`LOG(x);`). The CLI prints logs to stderr, the playground shows them in a Console tab, and every host gets them in the run result and the event stream.

## Why now

It is built on the final pieces: the event stream (R3), the CLI and playground on the runtime (R7, R8), statements that run in function bodies (X3), the built-in table (L5), and the grammar after L4.

## Build

1. **Grammar**: a call followed by `;` becomes a statement in `BodyStatement`. Only calls may stand alone (not any expression). Watch the LL(k) risk: `AssignmentStatement` also starts with a full expression (`target=Expression operator=… value=Expression ';'`), so a separate rule that also starts with an expression cannot be told apart before the `=` or `;`. If `langium generate` reports a conflict, merge the two: one rule `target=Expression (operator=… value=Expression)? ';'`, plus a check that a statement with no operator is a call (`call.statementNotACall` otherwise). No new warning may remain. Parse tests next to assignment (`x = …`, `.a.b = …`) and `let`.
2. **`LOG` in the built-in table**: `LOG(value)` / `LOG(value, label: TEXT)`, return type = the value's type.
3. **Checker**: a warning `call.logInSql` when a `LOG` sits in a part that compiles to SQL (inside a query clause, or inside a filter that will be pushed down): "this LOG runs in the database and will not print". A call statement whose function returns a value is fine (the value is dropped).
4. **Interpreter**: evaluate the value, emit a `log` event `{ value, label, range, time }`, return the value. Logs also go into the run result (`logs`), capped by `logEntries` (D36); when the cap is hit, set `logsTruncated: true` (not an error).
5. **Compiler**: `LOG(x)` compiles as `x`.
6. **CLI**: logs go to **stderr** as `file:line:col label: value` (value via `formatValue`, with newlines escaped as `\n`, D37). `--no-logs` turns them off; `--json` stdout stays parseable.
7. **Playground**: a **Console** tab next to Execution, listing log lines in order; clicking a line highlights its source range (reuse how Execution highlights). Wireframe style only (W2 restyles it).
8. **Spec**: §5.3.1 row, a short "Debugging" subsection (what prints and what does not: parts that run as SQL, the right side of a short-circuited `AND`/`OR`, branches not taken), §8.2/§9 for the call statement, §11. **Showcase** section.

## Output

Debug output everywhere a program runs.

## Test scenarios

- Log lines arrive in evaluation order; the value comes back unchanged (`LOG(2) + 1` is `3`).
- `false AND LOG(true)` logs nothing.
- `LOG` inside a query `WHERE` → warning `call.logInSql`, and the query still runs.
- `LOG(x);` as a statement in a function body and at the top level.
- `minab run --json` with logs on: stdout parses as JSON; stderr has the log lines.
- A logged text with a newline prints as one line.
- 150 logs with `logEntries: 100` → 100 entries and `logsTruncated: true`.
- Playground: the Console tab shows the lines of a gallery example that uses `LOG`.

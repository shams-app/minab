# L2 — Spec examples under test

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| L — Language | Mechanical | S | [L1](L1.md) | — | 0.2.0 |

## Goal

Every Minab example in the spec is parsed (and, where it can be, checked) by a test, and the spec's grammar block (§11) can no longer drift from `src/language/minab.langium`.

## Why now

Only `docs/showcase.md` is under test today. Two spec defects were found after Phase 1 for exactly this reason. Every later language phase changes the spec; this guard makes those changes safe. It runs right after L1, when the call syntax is final.

## Read

- `docs/query-language-spec.md` (skim the code blocks; read §11 fully)
- `docs/showcase.md` §14 (`daysSincePayment`), `examples/` (where `daysSincePayment` is defined in a `.minab` file)
- `test/parsing.test.ts` (how parse helpers are used)
- `.cursor/rules/spec-governance.mdc` (the narrow exception for examples that contradict the spec)

## Ask first

None.

## Build

1. `test/spec-examples.test.ts`:
   - extract every fenced code block from the spec and the showcase that has no language tag or the tag `minab` (skip `console`, `json`, `sql`, `ts` and others);
   - **parse** each one with no syntax errors;
   - **check** each one where a fixture schema makes sense: a fixture schema in `test/fixtures/spec-schema.json` with the tables the spec uses (`Customer`, `Order`, `Shipment`, …). Blocks that need tables the fixture does not have are parse-only;
   - blocks that are deliberately wrong (the spec shows an error on purpose) are listed in the test file with their section and a reason: `{ section: '§6.1', index: 2, expect: 'type.implicitCoercion' }`. Their expected code is checked. Do not mark blocks inside the spec file.
2. **Grammar block vs. grammar file**: a test that compares spec §11's grammar block with `src/language/minab.langium` (ignoring whitespace and comments) and prints the difference when they differ.
3. **Showcase §14**: define `daysSincePayment` where it is called (copy the definition from the example that already has it). This falls under the governance exception (a call to a function that is never declared contradicts the spec). Mention it in your status file for the owner.
4. If the new test finds an example that does not parse or a §11 difference: fix the **example** to match the grammar (the grammar is authoritative) when the governance exception applies; otherwise stop and ask.

## Files

`test/spec-examples.test.ts` (new), `test/fixtures/spec-schema.json` (new), `docs/showcase.md` (§14 only), spec examples only under the exception.

## Do not touch

The grammar, spec prose.

## Output

A guard that every later language phase must keep green.

## Test scenarios

- Break one spec example on purpose (remove a closing brace) → the test fails naming its section; undo.
- Change one rule in the §11 block only → the grammar test fails with a diff; undo.

## Done when

The new tests pass and catch both kinds of drift; `daysSincePayment` is defined in the showcase.

## Not here

Changing what the language means (L4). New examples.

## Later

None expected.

## If it grows

If many spec blocks cannot be checked with one fixture schema, keep them parse-only and list them under Later (lane L4) for a second fixture.

# X2 — Multi-key `KEY` and user functions inside a query

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| X — Execution | Design → Mechanical | M | [X1](X1.md), [L4](L4.md) | [D22](../decisions.md#d22), [D23](../decisions.md#d23) | 0.4.0 |

## Goal

`KEY` works when `GROUPBY` has several keys (a record of named keys, D22), and a simple user function can be called inside a query (it is inlined into the SQL, D23); any other function there is a **check** error, so `check` tells the truth.

## Why now

These are the last two query refusals. L4 added the `GROUPBY … AS` names; X1 completed the expression compiler.

## Read

- `src/language/minab-sql-compiler.ts`: the `KEY` handling (the "no single SQL form" refusal), `call()`
- `src/language/minab-type-checker.ts`: `inferGroupKeyRef`, `inferCallExpression`

## Ask first

None (D22, D23 are the approved proposals).

## Build

1. **Multi-key `KEY`** (D22): with several keys, `KEY` has a record type whose fields are the keys' names (`AS` name, else the last field name of a plain path). The checker types `KEY.<name>` and reports `query.unnamedGroupKey` for a computed key without `AS` (only when there are several keys). The compiler emits each key's grouped expression for `KEY.<name>` in `SELECT`, `HAVING` and `ORDERBY`. One key: unchanged.
2. **User functions in a query** (D23): when a query clause calls a user `fn` whose body is one tail expression (no statements, no recursion — direct or through other functions —, no host functions, no queries), the compiler inlines the body with the arguments put in place of the parameters (each argument compiled once; if an argument is used twice and is not a plain column or parameter, still correct: SQL evaluates it twice, which is fine because Minab expressions in SQL have no side effects). Any other user function in a query clause is a **check** error `query.functionNotInlinable` naming the reason (statements, recursion, host function).
3. **Spec** (approved by D22, D23): §2.2 and §4 (`KEY` with several keys), §8 (functions inside queries). **Showcase** sections.
4. Tests: SQL text, query cases on Postgres (`test/queries/cases/x2-*.cases.ts`), checker tests for the two new codes.

## Files

`src/language/minab-sql-compiler.ts`, `src/language/minab-type-checker.ts` (or validator), `src/language/diagnostics/codes.ts`, tests, spec, showcase, playground cheat sheet.

## Do not touch

The grammar (L4 added `AS`).

## Output

No construct is refused inside a query except statements and functions that cannot be inlined (both stated in the spec and caught by `check`).

## Test scenarios

- `GROUPBY .status, .customer.country AS country SELECT KEY.status AS s, KEY.country AS c, COUNT(.) AS n` returns the right groups.
- `GROUPBY .status, YEAR(.created_at) SELECT …` → `query.unnamedGroupKey`; with `AS year` it runs (needs L6; if L6 is not merged, use another computed key).
- `fn net(t: DECIMAL): DECIMAL { t * 0.9 }` in `WHERE net(.total) > 100` → inlined SQL, right rows, interpreted = compiled.
- A function with a `let` inside, used in a query → `query.functionNotInlinable` at check time.
- A recursive function in a query → the same code.

## Done when

All tests pass; spec and showcase updated.

## Not here

Running a query row by row in the interpreter (D23 option b, not chosen).

## Later

Inlining functions whose bodies have `let`s (substitute them), if users ask (post-1.0).

## If it grows

It should not.

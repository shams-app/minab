# H8 — Host safety fixes: endpoint guards, one runtime per schema, host checks

| Lane | Kind | Size | Depends | Decisions | Release |
|---|---|---|---|---|---|
| H — Hosts | Mechanical | M | [H3](H3.md), [Q3](Q3.md) | [D01](../decisions.md#d01), [D34](../decisions.md#d34) | 0.4.0 |

## Goal

A host that follows the guides gets a guarded run endpoint, with `forRoot` and with `forRootAsync`. Two different schemas never share a runtime. `createMinab` refuses host names that are language keywords. The runtime checks the result of a host function against its declared type.

## Why now

"Safe" is point 4 of "What production level means", and D01 says every program is untrusted input. The Later lists and questions of H3, Q3, R3 and R4 name these traps. Code read on `main` on 2026-10-11:

- `MinabModule.forRootAsync` passes **no guards** to the run controller (`src/nestjs/module.ts`, `build(...)` without `guards`). The endpoint is mounted only when `endpointPath` is given, and `endpoint.guards` from the factory is ignored. But `docs/guides/embedding.md` §3 and `docs/security.md` tell hosts to use `endpoint.guards`. And `docs/guides/shamsine.md` shows `forRootAsync` with `endpoint: { path, guards: [JwtGuard, WorkspaceGuard] }` in the factory. As written, that example mounts no endpoint. If a developer adds `endpointPath` to make it work, the guards are silently dropped, and anyone who can reach the route can run stored programs.
- `MinabService` caches the runtime by `schema.version` only. Two tenants whose schemas share a `version` share one runtime, so one tenant sees the other's tables (Q3's question; `docs/security.md` asks hosts to avoid it).
- A host input or host function named like a keyword (`from`, `loop`) is accepted by `createMinab`, but no program can use it (R3, R4 Later).
- A host function's result is not checked against its declared type (ADR 0002 §4.3; R3, R4 Later).

## Build

1. **Guards with `forRootAsync`.** Add `guards` to `MinabModuleAsyncOptions`, next to `endpointPath`. A route and its guards are fixed before the factory runs, so they belong there. Pass them to the run controller. If the factory's options still contain `endpoint.guards` or `endpoint.path` under `forRootAsync`, the app fails at startup with a clear message that names the fix. A guard must never be ignored without a word.
2. **One runtime per schema.** Two different schemas under the same `version` must never share a runtime. Key the cache by the `version` and a hash of the schema's content. Hash one schema object only once (for example with a `WeakMap` keyed by the object), so a loader that returns the same object costs almost nothing. Check the cost against Q4's budgets.
3. **Host names that are keywords.** `createMinab` refuses a host input or a host function whose name is a language keyword, with a clear error that names it. Take the keywords from the grammar, not from a hand-written list.
4. **Host function results** (ADR 0002 §4.3). The runtime checks each host function result against the declared type: the scalar type, and whether `null` is allowed. A wrong result is the run error `eval.hostFunctionResult` (a new code in the registry), with the function name and the expected type. A wrong value never reaches the program.
5. **Docs.**
   - The embedding guide §3 and the Shamsine guide show `endpointPath` and `guards` next to each other in `forRootAsync`.
   - `docs/security.md`: the guard point and the schema `version` point say what the code now does.
   - `src/nestjs/README.md` and `src/runtime/README.md`.
   - Regenerate `docs/reference/diagnostics.md` (`npm run docs:diagnostics`).

## Output

Endpoint guards that work with both module setups. Runtimes that never mix schemas. Clear errors for host mistakes.

## Test scenarios

- `forRootAsync({ endpointPath, guards: [DenyGuard], useFactory })`: a request to the endpoint gets 403, and no program runs.
- `forRootAsync` with `endpoint.guards` in the factory's options: the app fails at startup with the message.
- `forRoot({ endpoint: { guards } })` still works (the existing test).
- Two loader results with the same `version` and different tables: each request runs on its own schema. A program that reads a table that only one schema has gives the right answer for that tenant and a check error for the other.
- `createMinab` with a host input named `from`, or a host function named `loop`: a clear error from `createMinab`.
- A host function declared `INTEGER` that returns `"x"`, and one declared not nullable that returns `null`: the run error `eval.hostFunctionResult`. A correct result passes.

## Done when

- Every scenario has a test that fails without its fix.
- The NestJS example's end-to-end tests pass (with Postgres if you can, otherwise as CI runs them).

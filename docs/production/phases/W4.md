## Goal

The website is live at its domain, deployed from `main` by a workflow, with preview deploys for pull requests, fast caching of the large WebAssembly files, and the design guide's Step F checks automated where possible (Lighthouse, accessibility) and done by hand where not.

## Why now

The designed site is built (W3). V4 checks it before 1.0.

## Read

- `playground/design/README.md` Steps F and H
- `playground/vite.config.ts`, `playground/scripts/prepare.mjs`, `playground/package.json`
- Decisions D41 (host), D42 (versioning), D40 (domain), D09 (`@lhci/cli`, `@axe-core/playwright`, `@playwright/test`)

## Ask first

The host account and the domain must exist (owner). Ask for: the host project name, whether the deploy secret (API token) is set in the repository, and that the domain's DNS can be pointed at the host. The domain is `minab-lang.org` (D40). Recommended: Cloudflare Pages (D41).

## Build

1. **Host config** per D41. For Cloudflare Pages or Netlify: `playground/public/_headers` with `Cache-Control: public, max-age=31536000, immutable` for hashed assets (JS, CSS, PGlite `.wasm` and `.data`) and short caching for `index.html`; an SPA fallback (`_redirects`: `/* /index.html 200`, or the `404.html` copy the build already makes). `PLAYGROUND_BASE` only if served under a path.
2. **Workflow `deploy-site.yml`**: on push to `main` (paths `playground/**`, `src/**`): build the root (the playground compiles `src/language`), build the playground, deploy. On pull requests: a preview deploy with its URL posted to the run summary.
3. **Footer**: show the Minab version the site runs (D42), read from the root `package.json` at build time.
4. **Automated checks** in a new workflow `site-checks.yml` on the preview URL (or `npm run preview` in CI):
   - Lighthouse CI (`@lhci/cli`): performance ≥ 90 on the landing page, accessibility ≥ 95 on every route (budgets in `playground/lighthouserc.json`);
   - axe accessibility checks with Playwright (`@axe-core/playwright`) on every route in light and dark;
   - a Playwright smoke test: landing loads; `/play?example=booking-overlap` runs and shows "1 statement"; a tour lesson's goal can be met.
5. **Manual Step F checklist** (the visual list in `playground/design/README.md`): the session runs what it can (keyboard-only walkthrough, reduced motion) and writes the rest as a checklist for the owner in the status file. Status **`waiting for approval`** until the owner signs it.
6. **API reference** (G1): if `npm run docs:api` exists, publish its output at `/api/` on the same site (one build step).

## Files

`playground/public/_headers`, `playground/public/_redirects` (or host config), `.github/workflows/deploy-site.yml`, `.github/workflows/site-checks.yml` (new), `playground/lighthouserc.json`, `playground/tests/*` (Playwright, new), `playground/package.json` (dev dependencies, scripts), the footer component (version).

## Do not touch

Engine, state, hooks, content (except the footer version).

## Output

A live, checked website.

## Test scenarios

Listed in Build 4. Also: after deploy, the `.wasm` response has the immutable cache header (check with `curl -I`; write the output in your status file).

## Done when

The site is live at the domain; deploys and previews work; the automated checks pass; the owner signs the manual checklist.

## Not here

Launch material and the TV demo (W5).

## Later

Uptime monitoring (W5 adds it for the launch).

## If it grows

Preview deploys may move to Later if the host makes them hard. The live deploy, caching headers and the automated checks must stay.

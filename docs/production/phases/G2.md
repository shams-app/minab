## Goal

Shamsine's team (and its AI sessions) can wire Minab into `core/service` and `core/web` from one document: which Minab API serves each of Shamsine's GM cards (M.0–M.16), a recommended mapping from every Shamsine field type to a Minab type, how names, dates, money, inputs, tiers, messages and stored expressions work, and a list of changes the monorepo plan needs.

## Why now

Shamsine integrates at 0.3.0 (D02). Everything it needs exists after R5, H3, H5, E5, L3 and L6.

## Build

`docs/guides/shamsine.md`:

1. **Map of GM cards**: for M.0–M.16, the Minab API or entry point that serves it, with links (start from the table in `docs/production/phases/README.md`, "Shamsine cards M.0–M.16", and make it concrete: function names, options, examples).
2. **Field type mapping** — one row per `DatasetFieldDataType` value (all of them; count them from the enum), with the recommended Minab type and a note. A starting point to check against the real storage table:
   - text, longText, richText (raw string), email, url, phone, barcode, color, singleSelect → `TEXT` (email may be `CITEXT`);
   - integer, rating → `INTEGER`; decimal, currency, percent → `DECIMAL` (exact, D17); duration → `INTEGER` (milliseconds);
   - boolean → `BOOLEAN`; date → `DATE`; time → `TIME`; dateTime, createdAt, updatedAt, deletedAt → `DATETIME`;
   - multiSelect → `TEXT[]`; user, createdBy, updatedBy, deletedBy → `TEXT` (Shamsine ids are not UUIDs); users → `TEXT[]`;
   - linkToRecord → a `ref`; linkToList → a `collection`; lookup, rollup, formula, count → the type of what they compute, read-only;
   - numberRange, timeline, timeTracking, week, attachment, icon, canvas, location, address → `JSON` with the documented shape (from `AGENTS.md`'s storage table);
   - id → the primary key column (`TEXT`);
   - say clearly which types are not usable in comparisons beyond `is`/`isnot` (the `JSON` ones) until a richer type exists.
3. **The schema**: one Minab table per dataset; column name = field name (Dynodb uses it as the column), so `sqlName` is not needed; `primaryKey`; relations with `foreignKey`; `version` = a hash of the datasets' fields (D29); the schema is the read surface: build it per application (D01).
4. **Names**: Persian, Arabic and Turkish names work as they are; names with spaces use backticks (D12); examples.
5. **`expect`**: Shamsine's `MINAB_EXPECT_TYPES` (`text`, `number`, `boolean`, `date`, `dateTime`, `list`) → the Minab types for `prepare({ expect })` (`number` = `INTEGER` or `DECIMAL`; `list` = an array type: say which).
6. **Inputs and the clock**: `currentUser` (a record type: id, email, roles…), `url` (`JSON`), the user's time zone through the clock port (D21, D27).
7. **Where things run**: tiers from the analysis (R5) → browser worker for `local`, the NestJS module's `runStored` for `data`; the dependency list for re-running only affected expressions (M.9); batching (M.10, the wire format).
8. **Data port per application**: Dynodb has one Postgres database per application; create the data port from that application's connection (`queryFunctionDataPort` over TypeORM's `query`), inside the request's transaction when there is one.
9. **Messages in fa, ar, tr**: translate by diagnostic code with its params (D35); a table of the codes users meet most (from `docs/reference/diagnostics.md`), ready to paste into Shamsine's translation file.
10. **Stored expressions**: store `languageVersion` next to each expression; validate on save with `prepare` (M.6); messages for failed rules are stored by Shamsine (D45).
11. **Jest, CommonJS and Bun** (H1): what to install, how `core/service` imports it.
12. **Monorepo follow-ups** (for the owner to apply in `shams-app/monorepo`; this phase never edits it): M.1–M.3 point to this repo's phases and are done by them; M.0 can be closed with this guide and ADR 0002; `TODO.md`'s claim that `@shamsine/minab` "is published" (it was not, on 2026-10-01) is corrected; any card text that this guide contradicts (list each one with the line and the suggested new text).

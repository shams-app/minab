# Minab

Minab is a small language with two layers that share one expression sub-language:

- a **pipeline query layer** (`FROM / JOIN / WHERE / GROUP BY / HAVING / SELECT / ORDER BY / LIMIT`)
- a standalone **validation layer** (`VALIDATE`, `field` rules)

The full language reference lives in [`docs/query-language-spec.md`](docs/query-language-spec.md). This repo implements it with [Langium](https://langium.org).

## Status

Early bootstrap. The grammar in `src/language/minab.langium` mirrors the reference grammar in spec §7 and parses the example snippets from the spec (see `test/parsing.test.ts`). No semantic services (scoping, validation, type checking) are implemented yet — see "Next steps" below.

## Setup

```bash
npm install
npm run langium:generate   # generates src/language/generated/* from the grammar
npm run build               # generate + typecheck
npm test                    # run the parser smoke tests
```

`npm run watch` regenerates the grammar and recompiles on file changes.

## Working conventions

These carried over from language design discussion and apply to any future grammar change:

- No implicit type coercion.
- Every grammar addition must be checked for LL(k) parsing safety.
- Keyword casing is a deliberate convention: SQL-style pipeline keywords are uppercase (`FROM`, `WHERE`, `GROUP BY`, ...); loop/JSON/control-flow keywords are lowercase. Grep for collisions after each addition.
- The spec document is a controlled artifact — it changes only alongside (and in sync with) grammar changes, not ahead of them.
- Proposal → example review → explicit approval → implementation, in that order, for any language change.

## Next steps

Roughly in the order they'll likely come up:

1. **Scope provider.** Minab's sigils (`.`, `^`, `@alias`, `KEY`, `$`) resolve against a scope *stack*, not the AST-lexical scoping Langium assumes by default (spec §2.2). This is the first real custom service to write — everything else (cross-referencing, validation, IDE hover/completion) depends on it.
2. **Validator.** Semantic checks that aren't expressible in the grammar: `$` only valid inside a `field` rule, `KEY` only valid after `GROUP BY`, relation/traversal type-checking (scalar vs. `ref` vs. `collection`, spec §3).
3. **Open design questions (spec §8)** — in particular #6 (bare `alias.field` vs. required `@alias`) and #7 (implicit relation traversal depth), since both affect the scope provider's design.
4. **Deferred discussion items** (from design notes, not yet in the spec): null semantics across `ref` traversal / `LEFT JOIN` / comparisons, and whether Minab is read-only by design. Both need resolution before the scope provider and evaluator can be finalized.
